## Intent

**Problem:** GitHub Actions run `28955588184`, job `85913670217` failed in `ci / build-and-test` at `Run dapr init`; build, package validation, and Tier 1 tests had already passed. The raw log shows plain `dapr init` installed runtime `1.18.1`, then failed because Docker could not bind the Dapr placement health port `58080`; retries then failed immediately because the partial first attempt left `~/.dapr/bin/daprd` behind.

**Approach:** Align Hexalith.Builds Dapr bootstrap with Dapr-maintained guidance: install the Dapr CLI through the official `dapr/setup-dapr` action, initialize with an explicit `--runtime-version`, export the GitHub token and GHCR image-registry setting used by Dapr's own workflow, and add pre-init cleanup/port-free waiting so retries do not preserve a half-installed runtime. This spec is explicit approval to modify only the root-declared `references/Hexalith.Builds` submodule files named in the Code Map.

## Boundaries & Constraints

**Always:** Keep the fix in shared Hexalith.Builds Dapr bootstrap so Tenants continues consuming the reusable domain CI workflow instead of reintroducing hand-written CI. Preserve full `dapr init` semantics for Tenants Tier 2/Tier 3 because the tests require Redis, placement, and scheduler. Use explicit runtime version parity with the existing `dapr-version` input. Keep third-party action references pinned by immutable commit SHA where the surrounding workflow already does so.

**Ask First:** Halt before replacing full `dapr init` with `dapr init --slim`, adding service containers, changing Tenants test tiers, weakening or skipping Server/Integration tests, changing root Tenants workflow structure away from `Hexalith.Builds/.github/workflows/domain-ci.yml@main`, or modifying any submodule outside `references/Hexalith.Builds`.

**Never:** Do not hide the failure by making Dapr tests advisory, removing retries without replacing the partial-install recovery, pinning the Tenants caller to a local unpushed Builds ref, using recursive submodule commands, or accepting runtime `latest` drift when a CI input already names the intended Dapr version.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Dapr bootstrap healthy | `dapr-version: 1.18.0`, Dapr ports free | CI installs CLI `1.18.0`, runs `dapr init --runtime-version 1.18.0`, prints `dapr --version`, and proceeds to Tier 2 tests | Any init failure remains blocking |
| Dapr health port briefly occupied | Port `58080`, `58081`, or `50005` is temporarily occupied before init | Bootstrap waits a bounded interval before calling `dapr init`, matching Dapr CLI test-harness behavior | Timeout emits a clear port diagnostic and fails before partial init |
| Previous init attempt partially installed binaries | Retry starts after `~/.dapr/bin/daprd` exists or Dapr containers were partially created | Retry first uninstalls/removes Dapr runtime artifacts, then runs init again | If cleanup fails non-fatally, it logs and continues; init failure still fails the job |
| Runtime version drift | CLI version input is `1.18.0` but latest patch is newer | Runtime remains `1.18.0` because init passes `--runtime-version` explicitly | No implicit latest lookup is accepted |

## Design Notes

Official Dapr references checked on 2026-07-08:
- `dapr/setup-dapr` action metadata installs only the CLI and runs on Node 20 at `v2`/main.
- The action README says runtime initialization is a separate step and shows `dapr init --runtime-version=...` plus `GITHUB_TOKEN`.
- Dapr docs for GitHub Actions show `dapr/setup-dapr@v1` with explicit CLI version and `dapr init --runtime-version`.
- Dapr init docs state runtime defaults to `latest`, supports `--runtime-version`, supports `DAPR_DEFAULT_IMAGE_REGISTRY=GHCR`, and full init pulls placement, scheduler, Redis, and Zipkin containers.
- Dapr CLI E2E `installDapr` waits for `58080`, `58081`, and `50005` before init.
