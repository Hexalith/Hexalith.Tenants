## What Went Well

- Documentation work was treated as executable contract surface. The quickstart, contract reference, demo, timing guide, and compensating-command guide all gained tests that bind examples to current source.
- The team corrected inherited drift instead of layering new wording over it. Examples include the `BootstrapGlobalAdmin` domain, ULID-shaped command IDs, EventStore command route, HMAC fallback audience/key, configuration-command authorization, lifecycle rejections, and DAPR retry/dead-letter source anchors.
- Story split stayed healthy. Quickstart, contract reference, sample walkthrough, demo, timing, and compensation each kept distinct scope and linked to neighboring guides rather than duplicating them.
- Support-safe documentation became a consistent standard. The stories repeatedly removed or prevented raw token, full payload, secret, stack trace, and sensitive user-data exposure.
- The sample service became a better adoption proof without changing core domain behavior. The docs now explain the actual reusable path: `AddHexalithTenants()`, typed handlers, `MapTenantEventSubscription()`, local projection state, and fail-closed access checks.
- Review found meaningful issues and the team fixed them in the same story flow. That included high-value corrections in docs and scripts, not only spelling or navigation cleanup.

## Challenges

Charlie (Senior Dev): "The hard part was that documentation looked done before it was actually verified. Almost every story found prior assumptions that were plausible but wrong."

- Several existing docs and scripts came from older work and had to be treated as unaccepted prior state. The team had to audit before trusting.
- Live AppHost proof could not be claimed in this sandbox because Docker access was unavailable. The team kept that limitation explicit and relied on source-backed tests where live infrastructure was not available.
- `dotnet test` repeatedly built successfully but VSTest aborted in the sandbox with `SocketException (13): Permission denied`. The direct xUnit runner fallback became the practical validation path.
- The demo acceptance language implied plural live subscribers, while the current AppHost has one runnable `sample` subscriber. The final docs handled this honestly: one configured subscriber in the demo, with the same pattern available to additional services.
- Epic 8 surfaced that adoption docs are coupled to operational details: AppHost resource names, auth mode, DAPR component names, command status, and projection timing all affect whether the docs remain executable.

Murat (Test Architect): "The pattern is not just 'test the docs.' It is 'test the specific claims most likely to rot': routes, domains, roles, statuses, IDs, examples, and source file names."

## Key Lessons

1. Adoption documentation must be source-backed. Routes, domains, packages, command envelopes, enum values, topic names, and sample code should fail tests when they drift.
2. Documentation epics can uncover product defects. Epic 8 corrected Keycloak realm claims, demo script authentication, and test evidence gaps while staying inside adoption scope.
3. Live proof and source proof are different. Source-backed documentation tests can keep examples current, but runtime claims still require Docker/DAPR/Aspire evidence.
4. The EventStore command lifecycle must be explicit in user-facing docs. `202 Accepted`, command status states, persisted events, published events, query projections, and subscriber projections are distinct states.
5. "Undo" language is unsafe in an event-sourced access system. Corrections are explicit commands with their own authorization, rejection, command status, and audit evidence.
6. Phase 2 UI planning should inherit Epic 8's vocabulary: truth state, projection freshness, audit pending/available, fail-closed access, support-safe evidence, and explicit correction workflows.

## Significant Discovery Check

No significant discovery from Epic 8 invalidates Epic 9. Epic 8 reinforces the existing Phase 2 assumptions rather than changing them:

- UI plans already require truth-state vocabulary, command lifecycle feedback, audit proof, consequence preview, accessibility, localization, and FrontComposer dependency governance.
- Epic 8 confirms those are necessary, especially because source proof, command status, projection truth, subscriber catch-up, and audit proof are separate states.
- The current AppHost has one runnable Sample subscriber, so future UI/demo language should avoid implying multiple live subscribers unless implementation adds them.

Epic update required: no immediate Epic 9 rewrite. Carry the lessons into future UI implementation-story conversion.

- Do not claim a live reactive demo or full local quickstart proof unless AppHost, Docker, DAPR, auth, EventStore command status, Sample access transition, and audit/query evidence have actually run in a prepared environment.

- Do not use hidden undo language for access recovery; use explicit correction and compensating-command terminology.
