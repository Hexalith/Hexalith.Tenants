## What Went Well

- The team preserved the intended EventStore command path. Bootstrap and tenant governance commands flow through the command gateway and Tenants `/process` domain processor instead of adding per-command REST endpoints.
- Global administrator authority was modeled at the correct boundary. Assignment management uses `GlobalAdministratorsState`; tenant governance authorization uses trusted `actor:globalAdmin` envelope metadata populated by EventStore, not command payload fields or raw claims inside aggregates.
- Canonical aggregate identity was hardened. Tenant lifecycle events and rejections use `envelope.AggregateId`, preventing command body tenant IDs from retargeting operations.
- Structured rejection handling became stronger than originally planned. The epic added deterministic Problem Details mapping coverage for every Tenants rejection type and guardrails that prevent persisted rejection payloads from carrying prose or sensitive fields.
- Fail-closed behavior improved. `TenantStatus.Unknown` is ordinal zero, serializes by name, accepts unrecognized status names as `Unknown`, and blocks tenant mutations rather than defaulting to active behavior.
- Source-of-truth evidence was anchored in EventStore behavior. Publish failure after persistence remains an accepted command outcome for successful domain events, schedules drain recovery, and does not duplicate persisted source events.
- Documentation updates were made during the epic for event contracts, Problem Details, lifecycle duplicate rejections, fail-closed status behavior, and pub/sub outage expectations.

## Challenges

- Local VSTest execution repeatedly hit the known socket restriction: `System.Net.Sockets.SocketException (13): Permission denied` while the test platform starts its socket server. Story records consistently separated this environment blocker from product failures.
- DAPR prerequisite availability limited full local runtime evidence for Story 2.7. Direct xUnit execution proved EventStore actor publication and drain behavior; Tenants DAPR tests compiled and were skipped with the explicit prerequisite reason.
- Story 2.2 and Story 2.3 exposed a boundary that could have been blurred: global administrator set management is state-based, while tenant governance bypass is envelope-extension-based. Keeping those separate avoided circular authorization and claim parsing in aggregates.
- Story 2.4 introduced public contract churn by adding `TenantUpdated.UpdatedAt`. The compiler and `rg "new TenantUpdated"` were essential to update all source, test, projection, and documentation construction sites.
- Story 2.5 found a high-risk fail-open gap: `TenantStatus.Unknown` initially was not treated as non-active by tenant mutation handlers. Review fixed the aggregate guard and added direct coverage.
- Story 2.6 required touching shared EventStore boundary behavior. The safe fix was in the shared Problem Details/logging layer, not a Tenants-specific duplicate mapping pipeline.
- Story 2.7 relied on EventStore's existing drain contract instead of a new outbox. That was the right architectural choice, but it required careful tests to distinguish duplicate pub/sub delivery from duplicate persisted source events.

## Key Learnings

1. Trusted metadata must stay server-derived. Authority flags such as `actor:globalAdmin` are safe only after EventStore sanitizes client extensions and derives them from authenticated context.
2. Aggregate identity must come from the envelope, not the command body. This is now a core invariant for tenant lifecycle commands and should carry into Epic 3 membership/configuration work where applicable.
3. Unknown enum values are security-sensitive. Sentinel defaults must fail closed in serialization, read models, and aggregate command paths.
4. Structured rejection events are public contracts. Persisted rejection payloads should carry facts only; API-layer Problem Details composes titles, details, reason codes, and corrective actions.
5. Pub/sub is distribution, not source of truth. Stored EventStore events are durable; publication may fail and recover later, and consumers must remain idempotent.
6. Review loops caught real issues in every technical risk area: support-safe logs, ULID IDs, stale command names, missing audit fields, fail-closed status handling, Problem Details shape, and source-of-truth recovery.
