## Intent

**Problem:** The historical preview can dispatch from stale authority, confirm from a matching role alone, lose an in-flight attempt, and link unrelated audit as proof. It does not meet the current Epic 5 contract.

**Approach:** Complete Story 5.5's handoff with a current-state preview, recheck before one forward command, retain and reconcile its attempt, and link receipts only with deterministic evidence.

## Boundaries & Constraints

**Always:** Preserve original evidence and last-confirmed projection; require explicit role, current authority, safe width, complete preview, and fresh confirmation-time checks. Reuse the command gateway, one ULID attempt, aggregate lock, and status lookup. Confirmation requires the matching postcondition and a fresh ordered projection that has reached this verified command's committed event sequence. Separate command, projection, and audit states. Localize EN/FR copy and return focus.

**Never:** Infer historical role; double-dispatch; confirm from role or generic version advancement alone, or link from target/time coincidence; mutate history; add endpoints or public-contract changes beyond the approved status-proof extension; expose raw tracking data; enable global-admin correction.

**User decision (2026-10-03, option 1):** Extend the existing EventStore command-status proof with an optional committed aggregate event sequence and aggregate domain, and consume it in Tenants. Preserve reliable correction confirmation; do not replace acceptance with a permanently unverified Tenants-only flow. This expressly authorizes the required EventStore source/contract changes, without package updates, submodule pointer movement, commits, deployment, or nested initialization. Legacy or incomplete status evidence remains unable to verify.

**User decision (2026-10-04, closure remediation):** Approve all three separate blockers: repair dependencies through root-declared McpCli/Platform checkouts, remediate flagged secret content while preserving enforcement, and explicitly approve the six existing dependency revisions as validation prerequisites. The current flagged content is public GitHub SSH transport identity; permit that exact password-free identity without admitting other URI credentials. Preserve original baselines, existing external commits, package pins and history. No commits or pushes are authorized.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
| --- | --- | --- | --- |
| Eligible restore/change | Fresh preview, authority, explicit role; verified completed command with committed sequence | One add/change command; confirm matching postcondition only when the projection reaches that command's committed sequence beyond the baseline | Keep original and lock until terminal evidence or the approved bounded expiry |
| Conflict/already applied | Target/role, tenant, authority, width, or admission changes | Re-derive supported command or block; same state sends nothing | Show safe reason and recovery |
| Ambiguous/rejected | Request may have reached gateway, or domain rejects | Retain ID; safe status/same-ID retry; no false success | Distinct lifecycle and focus |
| Proof unavailable | Audit row lacks deterministic attempt link | No paired receipt link; projection confirmation stays separate | Show actual audit availability and recovery |
| Intervening role cycle | Baseline 5/Contributor; other events 6/Reader and 7/Contributor; own correction 8/Reader | Projection 6 cannot confirm correction 8; matching fresh projection 8 or later can | Keep pending while behind; missing or invalid command proof is unable to verify |
| Legacy, mismatched, or no-op status | Missing/invalid sequence, wrong command or aggregate scope, nonpositive event count | No projection-confirmed success; no-op remains already applied | Safe localized state and recovery; no fabricated proof |
| Platform retry or recovery | Durable command-specific event range exists, or only legacy terminal evidence exists | Preserve exact committed end sequence through normal completion and publication recovery; never derive it from the current aggregate head | Omit unavailable proof safely; existing status consumers remain compatible |

**Acceptance Criteria:**
- Given an eligible intent, when preview opens or role changes, then ten current facts and original evidence appear; missing facts block Confirm with recovery.
- Given confirmation or a competing tenant command, when current authority, projection, and admission are rechecked, then one retained attempt dispatches through the existing gateway and the aggregate remains locked until terminal evidence.
- Given any command outcome, when status and projection refresh, then lifecycle, projection, and audit remain distinct; only causal postcondition evidence confirms correction.
- Given verified completed status for correction sequence 8, when a matching fresh projection is still at sequence 6, then it remains unconfirmed; sequence 8 or later may confirm, while missing/invalid or mismatched attempt proof remains unable to verify.
- Given an older server or persisted status record, when new status fields are absent, then deserialization and existing command consumers remain compatible and correction confirmation fails closed.
- Given an audit candidate, when proof is evaluated, then only deterministic attempt-specific evidence creates both receipt links; otherwise the UI shows the truthful availability state and neither link.
- Given cancel, Escape, viewport change, refresh, or reconnect, when the surface reappears, then focus and tracking are preserved without a second logical command or unsafe copy.
