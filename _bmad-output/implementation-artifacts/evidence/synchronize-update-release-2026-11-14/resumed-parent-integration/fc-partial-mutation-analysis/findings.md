## Actual triage control and legitimate follow-through

`mutation-target-manifest.json` currently has `problemMutantTriage: []`. The schema actually enforced by `Get-TriageCount` (`eng/validate-stryker-reports.ps1:195`) is an aggregate entry with **segment, status, action, owner, rationale, count**. Matching segment/status entries require an allowed action and nonblank owner/rationale; their integer counts are summed. The validator compares each final report's Survived/NoCoverage/Timeout and non-exempt CompileError totals to those reviewed totals (381–394). It does not itself bind individual IDs or prove the rationale, ownership, human review, or a killing test; `blocking` is also syntactically in the action allowlist. Mechanical count coverage is not substantive acceptance.

Legitimate follow-through therefore needs complete original reports and actual tool exits first, then finite identification by segment, file, source span/replacement, report SHA and real status. Add meaningful tests for gaps; proposed cases are available for independent review. Any eventual accepted-equivalent or owned-deferral rationale must be real and source-specific. `blocking` remains unresolved work despite passing the entry's shape check. Do not add bulk counts, reinterpret the original statuses, invent owners/approvals, or change exclusions/thresholds to absorb survivors.

Only exact pinned nonexecuted compiler rollback metadata is exempt: CompileError, numeric ID, exact reason `Mutant caused compile errors`, and present empty coverage/kills arrays, under authenticated compiler metadata. Other malformed/unknown statuses still fail. Existing validator tests include untriaged Survived/NoCoverage/Timeout refusals. Both complete segments, Happy 80 and Error 60 tool exits, roots/cohorts, authenticated private tool and strict provenance remain required.
