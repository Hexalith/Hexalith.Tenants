## What Went Well

- The team preserved the domain boundary. Epic 1 used the existing query contracts and FrontComposer shell instead of adding Tenants-owned generic shell, event-store, or API scaffolding.
- Story 1.0 converted FrontComposer uncertainty into citable evidence. `FC-LYT`, `FC-CMD`, `FC-CNC`, `FC-A11Y`, `FC-L10N`, and `FC-DOC` were confirmed; `FC-TBL` caveats were isolated to the list implementation.
- The Tenants-specific UI composition worked. `TenantDataGrid`, `TruthStateBadge`, `ListSurfaceStates`, `TenantConfigurationView`, `MemberAccessReview`, and `SupportSafeCopyButton` delivered the read-only slice while staying local to Tenants' domain needs.
- The implementation consistently guarded projection truth. Stale, degraded, unauthorized, unavailable, invalid, and unknown states were kept distinct and review fixes closed false-success fallthroughs.
- Localization and selector discipline improved as the epic progressed. Later stories used surface-specific resource prefixes and `tenants-*` selectors more consistently after earlier review feedback.
- Story 1.8 produced useful readiness evidence mapping FR1 through FR9 to implemented surfaces, selectors, source-of-truth projections, and tests.

## Challenges

- Early planning documents still carried pre-implementation assumptions after the code had moved on. The main drift was Blazor Auto vs. implemented InteractiveServer, FC-LYT/FC-TBL readiness, Users as primary navigation vs. contextual Users, and ID language that called tenant/user IDs ULIDs.
- Several reviews found small but important accessibility and selector issues: missing row headers, leaked default truth-state selectors, invalid ARIA list structure, and test-stub localization drift.
- Shared state generalization created regression risk. Story 1.5 introduced an `Invalid` state that initially fell through on `/tenants/my`, rendering a false empty grid until review fixed it.
- Identity propagation was a recurring risk. Story 1.2 initially left list/detail query paths with a static `"system"` context risk; later self-audit and user lookup stories corrected requester/target behavior for their flows.
- Verification had environment friction. `dotnet test` remained blocked by the known .NET 10 Microsoft.Testing.Platform/VSTest issue, NuGet audit lookups were blocked by restricted network access, and broader Server/Integration test lanes still have pre-existing DAPR/AppHost evidence failures.
- The mutable `tests/test-summary.md` evidence file drifted across stories and was repeatedly missed in File Lists, reducing traceability until review corrected it.

## Key Learnings

- Treat story review findings as reusable acceptance rules. The repeated issues were not large design failures; they were small rules that should become checklist items before Epic 2 command work starts.
- Keep planning docs synchronized when an implementation decision becomes real. Retroactively relying on story notes is not enough when broader architecture and UI specs still say the opposite.
- Surface-specific selector and resource prefixes are worth enforcing. Shared components need explicit `TestId`/resource-prefix inputs on every surface to avoid hidden cross-surface test fragility.
- Command stories should not start until shared command foundations are explicit in code, not only in planning text. Epic 2 depends on command gateway, lifecycle state, one-at-a-time admission, projection re-query confirmation, safe rejection text, and audit handoff behavior.
- Support-safety must be handled before interop or feedback. Story 1.8's classifier-before-clipboard pattern is a useful template for later command/audit references.

## Significant Discoveries

Epic 1 did not invalidate the Epic 2 product direction, but it did refine the implementation path:

- Command stories should be split or gated if the shared command gateway, lifecycle reducer/model, projection re-query confirmation, rejection text catalog, and audit handoff states are not ready at Story 2.1 start.
- The old "Users as primary navigation" text is wrong for the implemented route model. Users remains contextual via `/tenants/my` and `/tenants/users`.
- Tenant/user identifiers are literal caller-supplied strings. Any doc that says these IDs are ULIDs is wrong for Tenants UI implementation.
- `FC-TBL` was resolved locally for Epic 1 with Tenants-specific grid/table composition; generic reusable grid improvements still belong in FrontComposer if they are needed by other domains.
