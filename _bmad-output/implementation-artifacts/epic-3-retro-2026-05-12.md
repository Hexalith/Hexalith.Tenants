## What Went Well

- Review discipline improved the implementation. Story 3.1 found two real acceptance gaps before closure: FluentValidation was not actually validating deserialized tenant payloads, and duplicate-user rejection lacked the existing role.
- The team chose the right abstraction point for RBAC. Extending EventStore to support optional envelope-aware Handle methods kept actor identity server-owned and avoided forgeable command payload fields.
- Story 3.2 created a reusable pattern that Story 3.3 could follow cleanly: null guard, disabled guard, RBAC, domain limits, NoOp, success.
- Security decisions were explicit. The epic documented GlobalAdmin bypass, extension metadata sanitization risk, empty-tenant bootstrap, self-removal/self-demotion policy, and default-deny behavior for unknown roles.
- Configuration behavior was intentionally modeled rather than improvised: same-value sets are NoOp, missing-key removal is NoOp, empty values are allowed, keys are opaque, and limits are enforced before producing events.
- Test coverage expanded with the risk: Story 3.2 moved TenantAggregate tests from membership behavior into authorization matrices, and Story 3.3 added boundary coverage for configuration limits and switch ordering.

## Challenges

Charlie (Senior Dev): "The hardest part was that Epic 3 asked the aggregate to answer a question it previously could not see: who is doing this?"

- Actor identity was not available to Handle methods at the start of the epic. The initial EventStore dispatcher silently skipped 3-parameter Handle methods, which meant the framework had to evolve before domain RBAC could be correct.
- Story 3.1 initially treated direct aggregate validation as enough, but the real runtime path validates the outer `SubmitCommand`. That created a gap between story intent and pipeline behavior.
- GlobalAdmin bypass remained partly split between domain capability and server-side population. The domain can read `actor:globalAdmin`, and extension metadata sanitization exists, but evidence in this retro did not show a production behavior that populates that extension from trusted GlobalAdmin state for normal tenant-management commands.
- The architecture language still contains a stale example using `state.Members` while the implementation uses `state.Users`. The story records already call this out, but future agents can still trip over it.
- Current full solution verification is blocked by local DAPR placement prerequisites. This is an environment readiness issue, but it still affects release confidence unless the integration environment is brought up.

## Key Lessons

1. Validate at the runtime boundary, not the convenient boundary. Typed validators alone did not run for tenant payloads inside `SubmitCommand`; the tenant-specific payload validator closed the actual path.
2. Domain authorization needs trusted actor context. Passing `CommandEnvelope` into Handle methods was safer than embedding actor fields in client-submitted command records.
3. Security work needs explicit bootstrap stories. Empty-tenant bootstrap and GlobalAdmin cross-tenant management are not edge cases; they define whether the first real tenant can be administered.
4. Review bounces are healthy when they are specific. Story 3.1 improved materially because review identified acceptance-level gaps with file and behavior evidence.
5. Small domain decisions deserve documentation. Empty configuration values, whitespace-only keys, character-count limits, same-value NoOp, and missing-key NoOp are all future compatibility contracts.
6. Stale architecture examples are a real implementation risk. The `Members` versus `Users` mismatch should be cleaned up so future story creation does not repeat defensive warnings.
