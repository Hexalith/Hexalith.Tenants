## Intent

**Problem:** Release run `30240946791`, job `89897853390`, reported success but created no release. Its source check accepted `b3d01c5`, `main` advanced to `d2e5a12` during the job, and Semantic Release treated the stale checkout as a successful no-op.

**Approach:** Revalidate the exact caller source in the shared release workflow immediately before Semantic Release, and add a caller-owned postcondition that only allows the Tenants Release workflow to finish green when a published GitHub Release tag resolves to the dispatched SHA.

## Boundaries & Constraints

**Always:** Preserve manual `workflow_dispatch`, the caller-owned exact-green-main preflight, protected-environment secret isolation, immutable Builds execution identity, and fail-closed publication. Keep the shared late guard reusable and place it after setup/build work but before any Semantic Release lifecycle or publish effect. Make the final caller check accept the release by exact tag commit, not mutable `main` or release ordering.

**Ask First:** Halt before committing or pushing either repository, selecting a new remote Builds execution SHA, dispatching a live release, changing protected environments/secrets, or broadening the fix to unrelated release tooling.

**Never:** Publish the stale dispatch SHA, check out a newer unqualified source, restore automatic `workflow_run` publication, suppress Semantic Release safety checks, infer success solely from exit code/artifact presence/latest-release ordering, expose credentials, or invent an unpublished Builds pin.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|---------------|----------------------------|----------------|
| Stable release | Checked-out SHA still equals live `main`; Semantic Release publishes a tag at that SHA | Shared guard passes and caller postcondition keeps the run green | Any API/malformed-identity error fails closed |
| Main advances before Semantic Release | Live `main` differs from checked-out dispatch SHA | Shared workflow exits nonzero before Semantic Release | Explain that the source became stale and must be redispatched after exact-source CI |
| Semantic Release exits zero without publishing | Reusable job returns success but no published release tag resolves to the dispatch SHA | Tenants postcondition fails the run | Report the missing exact-source release instead of a green no-op |
| Main advances after successful publication | Published tag resolves to dispatch SHA while `main` is newer | Caller postcondition passes | Do not require the released SHA to remain the current branch tip |

## Spec Change Log

## Design Notes

The two checks close different gaps. The shared guard prevents work from entering Semantic Release with an already stale source. The caller postcondition is the end-to-end success contract and catches any future exit-zero/no-publication path. Neither attempts to freeze `main`; a stale operator dispatch must fail and be repeated from the new green tip.
