- **Story 12.2: Audit Timeline and Consequence Preview Readiness.** Extended the dependency map with audit/consequence readiness rows and decisions for `FC-AUD`, grouped audit mode, `FC-CNS`, `FC-CMD`, `FC-CNC`, `FC-TOK`, `FC-A11Y`, `FC-L10N`, `FC-DOC`, and `FC-LYT`. Added readiness rows, alias mapping, named owners for unresolved readiness rows, retry/timeout/polling budget owners, allowed command-state transitions, SignalR delay/disconnect behavior, duplicate/out-of-order/stale/unknown/invalid message handling, safe copy, accessibility, localization, and copy-ready `blockedBy` examples. Code review resolved 3 decisions, applied 10 patches, verified 1 false-positive, deferred 4 items, and dismissed 4 items. Full Debug/no-restore solution gate passed with 731 passed and 5 skipped.
- **Story 12.4: Phase 2 UI Story Backlog with Explicit `blockedBy`.** Created `docs/tenants-ui-phase-2-story-backlog.md` with 15 candidate UI rows covering Tenant List, Tenant Detail, Create Tenant, Edit Tenant, User Management, Tenant Configuration, Audit Trail, My Tenants/User Search, and Global Admin Management. Enforced 12 mandatory row fields, literal arrays for `blockedBy`, backend evidence, FrontComposer dependencies, and evidence sources. Kept all candidate rows `planning-only` or `blocked`; no row was promoted to `ready` or `ready-with-approved-fallback`. Epic status in `sprint-status.yaml`: all four stories are `done`, `epic-12` remains `in-progress` by the existing file convention, and `epic-12-retrospective` moves from `optional` to `done` with this retrospective.

## What Went Well

- **The Phase 2 boundary held.** No source code, package references, generated UI files, backend endpoints, backend contracts, submodule pointers, or Phase 1 release gates were changed by the Epic 12 stories. `sprint-status.yaml` changed only for BMAD workflow tracking.
- **Dependencies became reusable contracts.** The stable `FC-*` IDs turned screen-level desires into citeable planning units. Future UI stories can cite `FC-AUD`, `FC-CNS`, `FC-CMD`, `FC-CNC`, `FC-TOK`, `FC-A11Y`, `FC-L10N`, and `FC-DOC` directly instead of relying on narrative assumptions.
- **Missing evidence was treated as evidence.** `FC-AUD`, `FC-CNS`, Storybook/component reference evidence, consequence/risk tokens, and toast batching policy stayed `missing` or `needs-confirmation` where the current checkout could not prove readiness.
- **The backlog is honest.** Story 12.4 produced 15 candidate rows and deliberately marked none as implementation-ready. That is the correct outcome for a dependency-governance epic whose job was to prevent hidden blockers.
- **Review caught schema drift before implementation stories copied it.** Review patches corrected destructive-workflow `FC-CNC` placement, `FC-LYT` readiness rows, `FC-AUD grouped mode` semantics, `needs-confirmation` glossary wording, `/api/commands` -> `/api/v1/commands`, `deployment-auth-readiness.md` -> `production-auth-readiness.md`, and the Blazor documentation mismatch for `FC-DOC`.
- **Command feedback got real failure-mode coverage.** Story 12.3 documented SignalR delay/disconnect, duplicate/out-of-order/stale/unknown/invalid messages, lost command IDs, browser refresh during pending state, polling unavailability, optimistic failure, and lifecycle dispatch failure. The UI does not yet implement those behaviors, but the future stories now have concrete failure cases.
- **Documentation language moved closer to the actual stack.** The review corrected Storybook-first language to Blazor component reference docs, Fluent UI Blazor demos, BlazorGallery-style catalogs, or equivalent. That matters because `Hexalith.FrontComposer` is Blazor/.NET, not a React Storybook package.
- **Prior auth contracts were preserved.** Story 12.4 cited completed backend evidence from Epics 9 through 11 and preserved tenant/user isolation, authorization, projection, and production-auth boundaries instead of inventing new backend requirements.

Dana (QA Engineer): "The best result here is that no row is `ready`. That sounds odd until you remember the mission: expose readiness truthfully. A false-ready backlog is worse than a blocked backlog."

## Challenges

Charlie (Senior Dev): "This epic made our uncertainty visible. That is good, but it means the next team cannot pretend the uncertainty is gone."

- **No Phase 2 UI story is implementation-ready yet.** Every candidate row still has unresolved FrontComposer dependency IDs, proposed/deferred fallbacks, missing evidence, or dependency-readiness gaps.
- **`FrontShell` legacy naming is still embedded in story keys.** The documentation now treats `FrontShell` as an alias for the current `Hexalith.FrontComposer` evidence, but the 12.1 story key and filename still contain `frontshell`. Renaming would ripple through BMAD artifacts and was correctly deferred.
- **Some schema conventions remain unresolved.** Review deferred AC traceability mapping, UX-screen to candidate-row mapping, row-level owner refinement, backend evidence grammar formalization, `evidence: missing` syntax overload, Phase 1 blocker column semantics, and exact evidence-anchor requirements.
- **`FC-DOC` remains underdefined.** The epic corrected Storybook language, but it did not establish the actual component-reference documentation convention future FrontComposer deliverables should use.
- **Audit and consequence readiness still lack source-backed components.** `FC-AUD` and `FC-CNS` remain missing in the current checkout; grouped audit mode remains a fast-follow sub-state, not a first-slice requirement.
- **Command feedback has adjacent source evidence, not an approved reusable contract.** Pending command state exists in the current checkout, but the Tenants-compatible API contract, confirmation thresholds, polling/status budgets, uniqueness scope, and toast batching policy remain `needs-confirmation` or `missing`.
- **Epic 12 did not drain the broader deferred-work register.** It added named owners for UI readiness rows, but R11-A1's larger cross-epic deferred-work triage remains open outside this planning artifact.
- **There is no Epic 13 definition in `epics.md`.** The next work is not a numbered epic yet. The practical next step is to promote or split Phase 2 UI candidate rows only after their `blockedBy` evidence changes.

Murat (Test Architect): "The deferred items are not failures. The risk is when deferred becomes invisible. Epic 12 did well on visibility; it did not yet solve closure."

## Critical Path Items

- Do not mark any Phase 2 UI candidate row `ready` while `blockedBy` is non-empty, fallback is only proposed/deferred, or backend evidence is incomplete.
- Do not treat `FrontShell`, `@hexalith/ui`, `useCommand`, `<AuditTimeline>`, or `<ConsequencePreview>` as current implementation evidence unless mapped to verified `Hexalith.FrontComposer` paths or recorded as missing/needs-confirmation.
- Do not promote audit timeline or consequence preview stories without resolving `FC-AUD`/`FC-CNS` strategy and audit retention/read-model assumptions.
- Do not invent per-story command feedback thresholds, pending identity scopes, polling budgets, or toast batching behavior locally. Use the owners and readiness rules from Story 12.3.
- Do not expand backend scope to satisfy UI consequence preview gaps unless product explicitly changes scope. Story 12.2 says consequence previews use already-loaded projection/read-model data unless scope changes.
- Do not convert Epic 12 outputs into implementation claims. The deliverables are planning/readiness artifacts.

## Significant Discoveries

- **The current checkout does not prove `FC-AUD` or `FC-CNS` exist.** Audit timeline and consequence preview readiness must remain blocked, fallback-approved, or source-evidence-backed before implementation.
- **Adjacent command evidence is not a reusable UI contract.** `PendingCommandStateService`, `PendingCommandRegistration`, and related FrontComposer concepts exist, but Tenants-compatible command lifecycle semantics remain `needs-confirmation`.
- **`blockedBy` needs literal array semantics.** Story 12.4's field encoding rules prevent dependencies from hiding in prose and make it mechanically obvious why a row is not ready.
- **Blazor documentation evidence is not Storybook evidence.** `FC-DOC` must use a Blazor-appropriate component/reference convention unless a real Storybook equivalent is introduced.
- **Endpoint citations matter even in planning docs.** Review caught `/api/commands` and corrected it to `/api/v1/commands` across affected rows. Planning artifacts are still contract surfaces.
- **The best next UI work is likely read-only first.** The destructive and high-impact workflows carry `FC-CNS`, `FC-CMD`, `FC-CNC`, and stricter token/copy/accessibility dependencies; read-only rows are better candidates once table/layout/a11y/l10n/doc evidence is resolved.
