# Story 9.7: Define Accessibility, Localization, and UI Acceptance Evidence

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a product owner planning UI implementation,
I want accessibility, localization, and responsive evidence requirements defined before UI stories start,
so that Phase 2 work cannot ship without proving the operational trust surface is usable.

## Acceptance Criteria

1. **Given** Phase 2 UI accessibility baseline is defined, **when** UI stories are drafted, **then** WCAG 2.1 AA is the baseline and WCAG 2.2 AA is the target where supported by the selected Fluent UI Blazor and FrontComposer stack, **and** the Operations Shell, tenant list, member table, command preview, command lifecycle feedback, and audit evidence surfaces are explicitly in scope.
2. **Given** keyboard and focus behavior is specified, **when** modal, preview, table, and command workflows are implemented, **then** all interactive elements are keyboard reachable, focus order follows task order, focus indicators work in normal, high-contrast, and forced-colors modes, dialogs trap focus when modal, escape behavior is safe, and focus returns to the launching row or action.
3. **Given** screen reader and status behavior is specified, **when** state labels, timestamps, status badges, row actions, and lifecycle changes are implemented, **then** accessible names, exact timestamp labels (not relative time alone), table headers, row relationships, sort state, and live-region announcements are required, **and** assertive announcements are reserved for rejection, failure, destructive blockers, or unable-to-verify states.
4. **Given** localization responsibility is specified, **when** UI text is implemented, **then** state labels, role names, timestamps, warnings, disabled reasons, recovery actions, and confirmation copy are localizable, **and** confirmation messages do not rely on concatenated sentence fragments assembled at runtime.
5. **Given** reduced motion and visual accessibility are specified, **when** lifecycle and state transitions are implemented, **then** reduced-motion users do not depend on animation to understand progression, **and** color contrast, forced-colors, and high-contrast behavior are verified.
6. **Given** UI acceptance evidence is planned, **when** implementation stories are marked ready, **then** required evidence includes desktop 1024px/1366px/1440px/wide, tablet 768px/1024px, mobile 375px/430px, keyboard-only navigation, NVDA or approved screen-reader review, automated accessibility checks, live-region checks, focus return, and disabled explanations without mouse hover, **and** acceptance scenarios include stale projection, rejected command, unknown confirmation, audit unavailable, last-owner warning, and permission-missing cases.
