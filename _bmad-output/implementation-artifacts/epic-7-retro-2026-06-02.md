## What Went Well

- The oversized deployment-readiness scope was successfully split into focused 7.6A-7.6E slices, making auth, DAPR/service invocation, health/readiness, pub/sub recovery, and final evidence capture independently reviewable.
- `Hexalith.Tenants.Aspire` now exposes a validated options model and tested Aspire application-model behavior while preserving hosting-only package boundaries.
- Production DAPR templates under `deploy/dapr` now use stable component names, receiver-specific deny-by-default access control, and explicit local/slim/production setup guidance.
- Story 7.3 resolved a high-value auth conflict: global-administrator-shaped principals now still require request tenant `system` and effective `eventstore:tenant=system` for protected Tenants command/query paths.
- Telemetry now distinguishes command, query, projection, rejection, no-op, failure, retry, and unsupported-domain outcomes with bounded dimensions and support-safe metadata.
- `/alive` and `/ready` are clearly separated. `/ready` depends on the DAPR state store and returns HTTP 503 when the ready dependency is unhealthy; `/alive` remains lightweight process liveness.
- Statelessness evidence improved beyond aggregate restart by adding projection/query reload coverage and architecture assertions against authoritative instance-local tenant state.
- Pub/sub recovery evidence preserves the right source-of-truth model: events are stored before publication, `PublishFailed` is stored-but-not-yet-published, and drain recovery republishes persisted events without duplicating the source stream.
- The final `docs/deployment-readiness.md` guide consolidates the evidence lanes and exposes a copyable support-safe evidence template.

## Challenges

Charlie (Senior Dev): "The biggest challenge was not implementation volume; it was evidence discipline. Several stories could have over-claimed from static tests or skipped DAPR runs if we were not strict."

Dana (QA Engineer): "VSTest socket denial stayed noisy across the epic. The direct xUnit fallback pattern worked, but every story had to separate runner limitations from product evidence."

Winston (Architect): "The production auth story exposed a real assumption conflict. Earlier Story 11.x material allowed a global-admin missing-tenant bypass, but Epic 7 required fail-closed behavior for protected Tenants endpoints."

Paige (Technical Writer): "Docs had to carry precise boundaries: local HMAC and local Keycloak are development paths, not production readiness proof; static docs checks are not live deployment proof."

Challenges observed:

- The environment repeatedly blocked VSTest before test execution with socket permission failures, requiring direct xUnit fallback evidence.
- Live DAPR/AppHost tests were discoverable and prerequisite-gated, but often skipped in this sandbox because Redis, placement, and scheduler were unavailable.
- Several senior reviews found support-safety gaps in diagnostics or telemetry, including raw exception leakage, health response data exposure, and unbounded telemetry metadata.
- Story 7.5 initially had projection reconstruction evidence that proved DAPR persistence but not the production projection query path; review corrected it to exercise a fresh projection actor.
- Story 7.6D initially used GUID-shaped identifiers in recovery tests; review corrected the tests to use repository-standard ULID-shaped sortable IDs.

## Key Learnings

1. Evidence lanes must be named explicitly. Static configuration tests, deterministic host tests, direct xUnit fallback, prerequisite-gated DAPR tests, and operator-run production evidence are different forms of proof.
2. Production auth needs a Tenants-specific fail-closed guard because a generic global-admin bypass can conflict with the Tenants platform tenant contract.
3. Health readiness must stay bounded. `/ready` should prove dependency readiness without submitting commands, invoking `/process`, or requiring production JWTs.
4. Support-safe output is a cross-cutting requirement, not just a logging concern. Health JSON, DAPR fixture diagnostics, telemetry span tags, assertion messages, docs, and evidence templates all need redaction discipline.
5. Deployment readiness documentation should not only list commands; it must identify what each command proves and what remains unclaimed when prerequisites are unavailable.
6. Pub/sub recovery should be framed around durable EventStore state and at-least-once delivery. It must not imply exactly-once delivery, global ordering, or simultaneous subscriber catch-up.
