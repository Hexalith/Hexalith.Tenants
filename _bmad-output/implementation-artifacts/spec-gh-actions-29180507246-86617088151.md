## Intent

**Problem:** Scheduled CI run `29180507246`, job `86617088151` (`ci / build-and-test`) fails at the **Restore** step. The committed EventStore submodule pointer (`da848c8`, pulled in by `1c72beb`) carries an internally inconsistent NuGet package graph: `Hexalith.EventStore.Admin.Server → Hexalith.Tenants.Contracts 2.4.2 → Hexalith.Commons.UniqueIds (>= 2.27.0)` conflicts with a `Hexalith.Commons.UniqueIds 1.0.0` resolution (NU1107), plus several NU1602/NU1604 "no inclusive lower bound" warnings-as-errors. Because cross-repo Hexalith deps resolve as centrally-pinned NuGet packages by default (`UseHexalithProjectReferences=false`), the submodule's own pins govern restore.

**Approach:** Advance the committed submodule gitlinks to the already-remote-reachable, newer working-tree commits (the coherent set the maintainer has staged locally), which restore cleanly, then apply the small Tenants-side migrations the newer platform requires: relocate two `FcShellOptions` usings (FrontComposer 2.0 package split) and implement the new `IReadModelStore.TryEraseAsync` member on three `Server.Tests` doubles. Deliver on a `fix/` branch with a PR.

## Design Notes

The governing contract (confirmed by the maintainer): **CI/CD consumes cross-repo Hexalith deps as centrally-pinned NuGet packages; development environments use Hexalith source project references** (`UseHexalithProjectReferences` false vs true, `Directory.Build.props:48-62`). Root cause is packaging drift **inside** the committed EventStore submodule that only surfaces in the package path CI runs — so the fix must make the *packages* consistent, not switch CI to project references. The maintainer's working tree already advances all five submodules to a set that restores cleanly; this spec commits that set and pays the Tenants-side migration cost of the newer APIs. FrontComposer's bump is **not** required to fix CI (FrontComposer was never implicated) — it is included only because the maintainer elected the full coherent set; the "Ask First" fallback narrows to EventStore-only if FrontComposer 2.0 proves invasive.

`TryEraseAsync` semantics (from `InMemoryReadModelStore`): `true` when the value was erased or already absent; `false` when a present value has a different ETag.
