## What Went Well

- Story 2.1 created a reusable Tenants command foundation without leaking generic infrastructure into the domain module. Later stories extended `ITenantCommandGateway`, `TenantCommandGateway`, `UnavailableTenantCommandGateway`, and `TenantCommandLifecycleState` instead of adding parallel command paths.
- Projection truth stayed central. Create, add-member, change-role, remove-member, and metadata edit all kept submitted intent separate from last-confirmed projection data and only moved to `confirmed` after authoritative re-query evidence.
- Domain semantics were preserved. Existing-member add remained a rejection, same-role change became `already applied`, last-owner removal stayed allowed with elevated friction, and metadata update did not invent same-state suppression.
- Support-safety improved over the epic. Reviews caught and fixed cross-command rejection copy leaks and expanded redaction for bearer/JWT/cursor/ETag markers.
- The remove-member flow proved the approved inline consequence-preview fallback in real UI code, including the ten required preview items, known unknowns, duplicate prevention, and honest audit handoff.
- UI test coverage scaled with each command flow. The UI suite grew through focused gateway, state, component, resource parity, and preservation tests, with final Story 2.5 evidence showing 316 UI tests passing via the xUnit v3 executable.

## Challenges

- Shared command status mapping was deceptively easy to get wrong. Stories 2.2 and 2.3 both found command-specific rejection text leaking through the shared status path until the code moved to command-neutral shared-status copy.
- Build/test execution had recurrent tooling friction. `dotnet test` repeatedly hit the known .NET 10 Microsoft.Testing.Platform/VSTest incompatibility, so validation depended on Release builds plus the generated xUnit v3 executable.
- Authorization reflection remains incomplete at the page wiring layer. Components expose `IsAuthorized` and command-surface parameters and fail closed when passed false, but `TenantDetailPage` still defaults several per-action authorization inputs rather than using a complete server-side reflection service.
- One-at-a-time command locking is not fully symmetrical. Story 2.5 locks member flows while metadata edit is active, but member command activity does not yet lock metadata editing because `MemberAccessReview` does not expose command-activity callbacks.
- Story 2.4 surfaced a UX decision point: after a confirmed removal, the target row disappears and the lifecycle panel unmounts, so confirmed/audit-pending feedback is not durable on the happy path.
- Story 2.4 used an inline preview panel with focus-on-open, Escape-to-close, and exact-row focus return, but not a hard keyboard focus trap. This is acceptable in current implementation evidence but narrower than the earlier modal-focused wording.

## Key Learnings

- Shared status lookup needs command-neutral copy by default. Command-specific rejection copy is safe only at submission time, where command context is known.
- Command state vocabulary must be richer than the original planning shorthand. `Previewed`, `DuplicatePrevented`, `AlreadyApplied`, `AuditDelayed`, and `MissingSupport` are necessary to avoid false success and false failure in real flows.
- Page-level authorization reflection should become explicit before Epic 3 high-impact flows. Component-level fail-closed behavior is not enough for lifecycle/configuration controls that carry broader blast radius.
- A delivered fallback should be reflected in planning docs quickly. The remove-member journey and historical backlog still described the inline consequence fallback as deferred even after Story 2.4 proved it.
- Test documentation should name the xUnit executable fallback. Repeating the same `dotnet test` failure across stories wastes review attention unless the documented local workflow reflects current SDK behavior.

## Significant Discoveries

- The approved inline consequence-preview fallback is implementation-ready for tenant-member removal. Docs that still say `ui-14` is blocked by a deferred inline fallback are stale for the delivered Epic 2 flow.
- The canonical feedback model needs implementation refinements for duplicate-prevented and audit-delayed states. These states exist in code and tests and should be treated as first-class in future command stories.
- Shared command status cannot safely infer the originating command from a correlation id alone. Shared rejection handling must stay command-neutral unless the status API adds command context.
- Server-side action availability reflection is still an architectural gap at the UI page wiring boundary. Epic 3 should address this before exposing tenant lifecycle/configuration controls.
