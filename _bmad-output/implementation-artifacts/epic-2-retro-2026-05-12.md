## What Went Well

- Reflection-based tests in Story 2.1 paid off immediately. Adding `LastGlobalAdministratorRejection` in Story 2.2 was covered by existing serialization and naming checks.
- The aggregate pattern stabilized quickly: static `Handle` methods, simple `Apply` methods, `DomainResult` outcomes, and tests through `ProcessAsync(CommandEnvelope, state)`.
- Story 2.3 deliberately made `TenantState` complete for lifecycle, user-role, and configuration events before all Handle methods existed. That reduced replay risk for later epics.
- Story 2.4 reused EventStore's command API, MediatR pipeline, DAPR actor flow, and event publication infrastructure instead of creating custom controllers or middleware.
- Reviews were substantive. They found real mismatches: unreachable bootstrap rejection logic, AC wording that did not match persist-then-drain behavior, stale file lists, and brittle processor-mismatch detection.
- The post-Epic-2 carry-forward was well-scoped and effective: typed exception handling replaced dependency on obsolete exception-message text.

## Challenges

Bob (Scrum Master): "No blame. The pattern is that the team did hard integration work at the boundary between Tenants and EventStore, and that boundary kept shifting under our feet."

- Story 2.2 discovered a missing rejection contract (`LastGlobalAdministratorRejection`) after Story 2.1 had supposedly completed the contract surface.
- DAPR and EventStore dependency alignment required package changes and follow-up fixes, including `Microsoft.Extensions.Configuration.Binder`.
- Story 2.4's original AC #5 described command success on pub/sub failure, while EventStore behavior returns `PublishFailed` after persisting events and scheduling drain recovery. The story had to be corrected to match the framework contract.
- The domain processor fall-through path initially relied on brittle string matching and missed the real typed `MissingApplyMethodException`.
- Integration tests are sensitive to EventStore API evolution. Current verification now fails because `SubmitCommandRequest` is ambiguous between `Hexalith.EventStore.Contracts.Commands` and `Hexalith.EventStore.Models`.

## Epic 3 Preparation

Epic 3, "Tenant Membership, Roles & Configuration," builds directly on Epic 2's choices:

- It depends on `TenantState.Users` and `TenantState.Configuration` replay behavior created during Story 2.3.
- It relies on the same aggregate Handle/Apply pattern established in Stories 2.2 and 2.3.
- It introduces domain-level authorization and role boundaries, which the architecture explicitly treats as business logic in aggregate Handle methods.
- It increases the importance of command actor identity, user context, and tests that verify unauthorized behavior.

Winston (Architect): "The preparation signal is clear: Epic 3 should lean into the TenantAggregate foundation, but be strict about role invariants and caller context. That is where security bugs would hide."

Alice (Product Owner): "Since current sprint status already shows Epic 3 and later epics as done, this section is retrospective continuity rather than a start gate. The lessons still matter for any corrective work."

## Key Lessons

1. Contract stories need a safety valve for missed domain outcomes. Reflection tests helped, but Story 2.2 still found a real missing rejection type.
2. Aggregate tests should exercise EventStore dispatch paths, not only direct Handle calls. The `ProcessAsync` pattern caught more realistic integration behavior.
3. Framework behavior must be treated as a product contract. Story 2.4 improved when AC #5 was rewritten to match persist-then-drain semantics.
4. Exception-message matching is fragile. Typed exceptions or explicit routing contracts are safer at Tenants/EventStore boundaries.
5. Story records are valuable when they include review outcomes, rejected findings, and post-review corrections. Epic 2's audit trail is much stronger because of those records.
6. Current verification belongs in the retro, even when it is inconvenient. A historical green run does not replace a present compile failure.
