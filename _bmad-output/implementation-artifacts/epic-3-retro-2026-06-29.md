## What Went Well

- The team preserved projection truth across lifecycle and configuration flows. Lifecycle status and configuration values only move to confirmed after authoritative re-query evidence.
- Story 3.1 created a useful blocked-state guardrail before Story 3.2 enabled FR15. That avoided exposing lifecycle controls as casual actions while the governance decision was still unresolved.
- The approved inline consequence-preview fallback was applied consistently to high-impact lifecycle and configuration flows without building a generic FrontComposer replacement inside Tenants.
- Support-safety stayed visible in the implementation: raw payloads, tokens, correlation ids, ETags, cursors, stack traces, and sensitive values were kept out of user-facing copy.
- Tests grew with the risk surface. Story evidence records UI executable passes from 340 tests in Story 3.1 through 446 tests in Story 3.4, and Story 3.5 later records 652 UI tests plus focused REST/query-handler coverage.
- Story 3.5 corrected a real architectural regression: tenant reads now use Tenants REST endpoints instead of a retired projection actor path.

## Challenges

- Lifecycle scope changed during the epic. FR15 started as blocked by high-impact governance and was later reclassified as reversible lifecycle availability control, while hard tenant deletion remained out of scope.
- One-at-a-time command locking had to be fixed more than once. Story 3.2 and Story 3.4 both needed review fixes to hold command activity through accepted/projection-pending states until projection truth resolved.
- Focus management was repeatedly under-specified in implementation. Story 3.2 and Story 3.4 both needed focus-loop or modal/focus-trap hardening during review.
- Degraded, unavailable, and unknown projection states were sometimes mapped to authorization failures. Story 3.1 and Story 3.3 both needed reason-honesty fixes.
- Configuration preview scope remains conservative because the PRD still leaves open whether every configuration edit needs a preview or only high-risk keys.
- Sprint tracking drift was identified and reconciled. Story 3.5 is a completed Epic 3 artifact, and the current sprint-status file lists it with Stories 3.1 through 3.4.

## Key Learnings

1. Guardrail stories are useful when governance is unclear. Story 3.1 let the UI be honest before Story 3.2 was safe to implement.
2. Command locks must be tied to projection truth, not just gateway completion. Accepted and projection-pending states still block other tenant command surfaces.
3. Focus containment is a high-impact flow invariant. A flow that claims destructive or high-impact confirmation needs tested focus-loop/focus-return behavior.
4. Unavailable reasons must describe the real system state. Data unavailability is not the same thing as missing permission.
5. Defect-fix stories that change architecture-critical behavior need sprint-status visibility, even when they are not part of the canonical epic feature list.

## Significant Discoveries

- FR15 disable/enable is reversible lifecycle availability control, not hard tenant deletion. Hard tenant deletion remains out of scope for the UI.
- The Tenants UI read path could not depend on `TenantsProjectionActor`; it had to use the Tenants REST read endpoints and preserve ETag/freshness metadata.
- Command-lock retention and focus containment are not incidental implementation details. They are shared safety requirements for all high-impact command surfaces.
- Sprint-status regeneration can hide completed defect-fix stories. That creates retrospective and readiness ambiguity unless reconciled explicitly.
