## What Went Well

- The team preserved the boundary from Epic 4. Consumer-local projections stayed in Client; centralized tenant discovery moved into server read models and query endpoints.
- Story 5.1 used EventStore's `EventStoreProjection<TReadModel>` pattern correctly: Apply methods live on read models, projection classes stay mostly shell-like, and assembly scanning owns discovery.
- Review caught projection domain drift. `TenantProjection` and `GlobalAdministratorProjection` now have explicit domain protection, and `TenantIndexProjection` intentionally uses `"tenant-index"` to avoid scanner conflicts.
- Story 5.2 turned an architectural uncertainty into an explicit handoff: `CachingProjectionActor` is query-side caching, not event fan-in. Event fan-in needs a subscription host, shared state key, ETag write discipline, and explicit projection invalidation.
- Story 5.3 implemented query contracts and response DTOs in Contracts, giving consuming code stable types for tenant details, summaries, memberships, members, and pagination.
- Authorization behavior was modeled in the actor rather than smeared across controllers. REST controllers translate HTTP to query requests; the projection actor handles tenant membership and GlobalAdmin checks.
- The audit endpoint was made explicit instead of half-built: GlobalAdmins receive a not-implemented response, while non-admins receive forbidden, preventing endpoint capability leakage.

## Challenges

Charlie (Senior Dev): "Epic 5 was where the simple word 'query' hid a lot of machinery: projection domains, actor routing, ETags, pagination, and authentication all had to agree."

- Cross-tenant indexing is not just another per-aggregate projection. Fan-in events update a shared index, so concurrency and invalidation had to be designed explicitly.
- Naming conventions were not enough by themselves. Story 5.1 needed domain pinning, while Story 5.2 needed a distinct derived domain to avoid duplicate projection registration.
- The story text originally expected full audit query behavior, but Story 5.3 made an MVP decision to return 501 for authorized admins and defer the full audit implementation.
- Query authorization has two layers: API authentication and domain authorization. Story 5.3 addressed domain authorization, but the host-level JWT authentication pipeline was later found missing.
- Runtime readiness lagged behind unit-level confidence. The post-epic carry-forward `post-epic-5-r5a1-tenants-jwt-auth-wiring` documents that protected `/api/tenants/*` routes return 500 until JWT registration and middleware ordering are fixed.

## Key Lessons

1. Projection domain names are operational contracts. A convention-derived name that compiles can still route incorrectly or collide during scanning.
2. Fan-in read models need hosting design, not just Apply methods. Shared keys require ETag conflict handling and explicit cache invalidation.
3. Query authorization is split by layer. Unit tests for actor RBAC are necessary, but they do not prove the ASP.NET authentication pipeline is wired.
4. Deferred scope should be explicit at the endpoint. Returning 501 after GlobalAdmin authorization is clearer and safer than pretending audit queries are complete.
5. Cursor pagination needs a stable ordering rule. Sorting by tenant ID is a simple, testable contract for both list tenants and user-tenants queries.
6. Post-epic defect stories are part of the retro truth. Story completion and release readiness diverged here, and the sprint status should make that visible.

Stakeholder acceptance: Not confirmed from available artifacts.

Unresolved blockers: Critical JWT authentication pipeline wiring for `/api/tenants/*`; old post-Epic-1 readiness gate still ready-for-dev; full audit query behavior remains deferred beyond MVP.
