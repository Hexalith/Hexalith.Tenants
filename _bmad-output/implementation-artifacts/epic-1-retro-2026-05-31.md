## What Went Well

- The solution structure converged on the intended `.slnx` entrypoint without introducing a legacy `.sln`.
- Package boundaries became executable rules rather than convention-only guidance. Guard tests and package validation now check packability, central package management, dependency boundaries, and host/test/sample leakage.
- CI moved beyond build/test into release-quality evidence: coverage gates, exact five-package validation, pinned actions, root-only submodules, and package-only consumer smoke validation.
- Story 1.4 validated the actual adopter experience through generated consumers for Contracts+Client, Testing, and Aspire instead of relying only on in-repo project references.
- Senior review loops found meaningful defects and converted them into durable tests, especially around deterministic SDK setup, missing coverage data, package dependency fixtures, and consumer restore source handling.

## Challenges

- Several validation commands behaved differently across environments. VSTest socket transport was blocked in the sandbox, while full evidence passed in a more capable environment.
- Package validation became stricter during Story 1.4 and initially broke synthetic test package fixtures from Story 1.3. The stricter rule was correct, but fixtures needed to model real package dependency metadata.
- The coverage gate initially used assumptions from synthetic Cobertura data and test-file targets. Real coverlet output required production-file targets, case-insensitive branch flags, and scoped line coverage aggregation.
- The local package smoke version exposed a release-mechanics edge case: EventStore source-project dependencies inherit the Tenants package version during local CI packs, producing benign `NU1603` resolution-up diagnostics for smoke packages.
- Documentation drift appeared immediately after implementation: submodule setup instructions and package validation descriptions lagged the actual source repo behavior.

## Key Learnings

1. Generated consumer projects are the right validation boundary for package adoption. They catch problems project-reference tests cannot see.
2. Coverage gates need to fail closed when expected scoped data is missing; otherwise a broken gate can report success.
3. Root-only submodule policy must be repeated in contributor-facing docs because it affects clone, CI, and package restore behavior.
4. Story-level evidence should distinguish sandbox limitations from product defects, then re-run in a capable environment before marking the story done.
5. Planning docs should track implemented package dependency boundaries because NuGet metadata is part of the public developer contract.
