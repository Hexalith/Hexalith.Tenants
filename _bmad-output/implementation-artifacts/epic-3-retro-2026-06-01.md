## What Went Well

- Tenant owner workflows stayed inside the aggregate domain model. Membership, role, and configuration rules are enforced in pure `TenantAggregate.Handle` methods instead of controllers, client code, or EventStore tenant validators.
- The team consistently applied the Epic 2 fail-closed lessons. `TenantRole.Unknown` remains non-privileged, role payloads serialize by name, and invalid roles do not create membership or role-change events.
- Tenant scope was hardened across the epic. Story 3.2 exposed command-body tenant ID leakage, and later stories aligned tenant-scoped success and rejection payloads to `CommandEnvelope.AggregateId`.
- Role boundaries became explicit and tested. Reader, Contributor, Owner, missing-member, cross-tenant, and trusted global-admin paths now have focused aggregate and conformance coverage.
- Configuration behavior became precise. Set/update, same-value no-op, missing-key rejection, exact key preservation, whitespace-key compatibility, and key/value/count limits are documented by tests and public docs.
- Story 3.8 kept concurrency in the correct layer. EventStore owns bounded persistence-conflict retry, terminal conflict status, idempotency timing, and HTTP 409 mapping; Tenants aggregates remain pure domain handlers.
- Story records consistently documented validation reality: VSTest socket startup is blocked in this sandbox, while direct xUnit fallback and Release builds provide usable evidence.

## Challenges

- Several current-sprint story files superseded older historical artifacts with overlapping names. The team had to avoid following stale broader-scope files such as older combined role/configuration stories.
- Envelope aggregate identity discipline emerged incrementally rather than being fully enforced in the first story. This caused repeated review findings until the pattern was applied across add, remove, change-role, and configuration handlers.
- Configuration semantics had hidden product decisions. Missing-key removal changed from historical no-op to structured rejection, while whitespace-only keys stayed accepted for compatibility and needed explicit tests/docs.
- Public docs lagged behind implementation in a few places. EventStore command docs still described command submission as non-idempotent, and the configuration reference omitted the new command-concurrency option.
- Optimistic concurrency acceptance criteria crossed the Tenants/EventStore boundary. Aggregate-only tests were insufficient; evidence had to come from EventStore actor/API behavior plus ordered Tenants domain semantics.
- Normal `dotnet test` remained blocked by sandbox socket permissions. Story records handled this well, but the project should keep direct xUnit fallback instructions visible for local agent workflows.

## Key Learnings

1. `CommandEnvelope.AggregateId` is the canonical managed tenant ID for aggregate command handling. Command-body `TenantId` is payload data and must not retarget emitted tenant-scoped events or rejections.
2. Domain RBAC belongs in Tenants aggregate handlers for Tenants-owned commands. EventStore validators are the API gate and consuming-service authorization boundary, not a replacement for aggregate rules.
3. Trusted global-admin authority must be exact and server-derived: `actor:globalAdmin == "true"` only after gateway sanitization and claims transformation.
4. Configuration keys are exact strings. Accepted key text is preserved, dot-delimited namespaces are a convention, and no hidden normalization should be introduced.
5. Persistence conflicts are infrastructure outcomes, not Tenants domain rejection events. EventStore should retry only before `EventsStored`; after that checkpoint, recovery must not re-persist.
6. Public docs need verification, not assumption. Story completion notes are good candidates, but each proposed doc change must be checked against code before editing.

## Next Epic Preview

Epic 4: Consuming Services Can React to Tenant Events

- Membership events now represent add, remove, and role-change behavior with fail-closed role serialization.
- Configuration events and rejections are precise enough for consumer projections to react safely to key changes.
- EventStore command outcomes distinguish domain rejections, no-op, idempotent duplicates, and infrastructure concurrency conflicts.
- Consumers must assume at-least-once pub/sub delivery and build idempotent local projections.

Epic update required: No.

## Significant Discovery Check

Epic update required: No.

Significant discoveries handled inside Epic 3:

- Several handlers initially used command-body tenant IDs in emitted payloads. The resolved invariant is that `CommandEnvelope.AggregateId` is canonical for tenant-scoped payloads.
- Missing configuration key removal is now a structured `ConfigurationKeyNotFoundRejection`, not a no-op.
- Whitespace-only configuration keys remain accepted for backward compatibility and are documented as preserved exactly.
- EventStore command submission is idempotent by `messageId`/`causationId`, and persistence conflict retry is controlled by `EventStore:CommandConcurrency:MaxPersistenceConflictRetries`.

These discoveries reinforce Epic 4 story guardrails but do not invalidate the Epic 4 plan.
