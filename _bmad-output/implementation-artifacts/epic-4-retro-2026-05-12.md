## What Went Well

- The epic stayed faithful to the "thin Client package" boundary. Client references Contracts and infrastructure packages, not Server or the command API.
- `AddHexalithTenants()` became the single adoption point, while still allowing custom options and custom projection store registration.
- The team corrected package assumptions quickly. Story 4.1 discovered that `AddDaprClient()` came from `Dapr.AspNetCore`, not `Dapr.Client`, and the implementation adjusted rather than forcing the original story text.
- The event-processing path matured through review. Story 4.2 added explicit processing results, safe dedup cleanup on failure, no-handler behavior, invalid-payload behavior, clone isolation, and serialized per-tenant projection updates.
- The sample made the integration contract concrete. `Program.cs` demonstrates DI registration, CloudEvents middleware, DAPR subscribe handler mapping, tenant event subscription mapping, and local projection access checks with a small code surface.
- Documentation landed with the implementation. The idempotent event processing guide explains at-least-once delivery, `MessageId` deduplication, handler idempotency, and production deduplication choices.
- Tests followed risk. Client tests grew from DI registration checks to processor, projection, handler, state isolation, and failure-mode coverage; sample tests verify access behavior and handler logging without requiring live DAPR infrastructure.

## Challenges

Charlie (Senior Dev): "The most useful friction was that the story assumptions were close, but not exact. DAPR package shape, EventStore's flat envelope, and duplicate processing all had little traps."

- The original Story 4.1 dependency note said `Dapr.Client` was enough for `AddDaprClient()`. It was not. The team had to switch the Client project to `Dapr.AspNetCore`.
- The story initially treated DI idempotency as a simple sentinel problem. Review found that option-registration sentinels could suppress required core registrations, so the registration flow had to separate core service guarantees from options deduplication.
- The event envelope required careful interpretation. For tenant domain events, envelope `TenantId` is the platform scope and `AggregateId` is the managed tenant ID used by projections.
- In-memory projection state had aliasing and race risks until the review follow-up added clone-on-read/write behavior and per-tenant synchronization.
- The default deduplication store is intentionally in-memory and unbounded for MVP use. The documentation names production alternatives, but production behavior still needs an explicit durable or bounded strategy when consumers require it.
- Full live DAPR behavior remains dependent on environment readiness. Story records distinguish Tier 1 tests from DAPR sidecar verification; the workspace history already shows that missing DAPR placement can block broader integration runs.

## Key Lessons

1. Integration stories need dependency verification early. Package ownership for extension methods is a build-time fact, not a planning assumption.
2. Idempotent registration is more than "do not duplicate descriptors." Core registrations must still be guaranteed when consumers preconfigure adjacent services.
3. Envelope metadata semantics must be documented near the code. `AggregateId` versus envelope `TenantId` is a correctness boundary for tenant projections.
4. At-least-once delivery should shape the API, tests, and docs together. Deduplication behavior, retry-after-failure behavior, and idempotent handler patterns are one design surface.
5. In-memory test-friendly infrastructure still needs production warnings. The default projection store and dedup dictionary are useful for samples and simple consumers, but production consumers need explicit durability choices.
6. Local consumer projections and centralized tenant query projections solve different problems. Epic 5 should reuse lessons from Client projection safety without copying the Client package's in-memory assumptions.

## Next Epic Preparation: Epic 5

Epic 5, "Tenant Discovery & Query," depends on the event surface proven in Epic 4 but changes the ownership model:

- Epic 4 local projections live inside consuming services and support runtime access enforcement.
- Epic 5 server-side read models serve administrative discovery, user membership lookup, audit queries, and cursor-paginated APIs.
- Epic 5 needs projection persistence, query authorization, cross-tenant indexing, and conflict handling for shared indexes.

Alice (Product Owner): "Epic 5 is where users stop asking, 'Can services react?' and start asking, 'Can I find, inspect, and audit tenants from the tenant service itself?'"

Winston (Architect): "The Epic 5 plan still looks sound, but it must not inherit Client's MVP in-memory posture. Server-side query projections need DAPR state store design, index keys, pagination, and authorization filters from the start."

No significant discovery from Epic 4 requires changing Epic 5's purpose. The main preparation risk is conflating consumer-local projection behavior with centralized query read models. The second risk is postponing concurrency design for the cross-tenant index.
