## Deferred from: code review of 10-1-optimistic-concurrency-for-tenant-read-model-writes (2026-05-18)

- Add retry backoff/jitter between guarded-save attempts in `TenantProjectionWritePolicy.SaveWithOptimisticConcurrencyAsync` to dampen index-singleton dogpiles under sustained N-way contention. Spec mandates only `MaxAttempts = 3`; immediate retry is compliant but operationally aggressive. Track as a write-path operational follow-up.
- Add a defensive `MaxAttempts >= 1` validation (or static assert) in `TenantProjectionWritePolicy.cs:12` so a future edit to `0`/negative cannot silently fall through to `throw new UnreachableException()`. Cosmetic safety net.
- Thread `CancellationToken` from the HTTP `POST /project` endpoint through `ProjectionDispatcher.DispatchAsync` → `TenantProjectionHandler.ProjectAsync` → `TenantProjectionWritePolicy`. Story 10.3A/10.3B explicitly owns the projection cancellation API; today the policy receives `default(CancellationToken)`, so client disconnect/SIGTERM cannot abort the retry loop. Tracked by 10.3B.
- Audit projection write path (`audit:{tenantId}`) still uses plain `SaveStateAsync` without ETag and is invoked between the two guarded writes. Under partial-success retry (index exhausts after tenant + audit commit, caller replays), audit `Entries` can duplicate if `TenantAuditProjection` is append-style rather than full-replace. Story 10.2 (`10-2-audit-projection-write-safety`) explicitly owns this; verify append-vs-replace semantics there.
- Validate `request.AggregateId` is non-empty in `TenantProjectionHandler.ProjectAsync`. An empty `AggregateId` produces the stable garbage key `"projection:tenants:"` and passes the policy's non-whitespace guard because of the prefix. Pre-existing input-contract gap that belongs upstream in `ProjectionRequest` validation or the `/project` endpoint, not in this story's helper.
- Singleton-index starvation under N-way concurrency (>3 simultaneous distinct-tenant writers all racing for `projection:tenant-index:singleton`) can throw for some callers despite the retry budget. Per AC2 the bounded-retry policy is the documented contract; document operationally if it ever becomes a hot-path issue.
- Classify DaprClient transport exceptions (`DaprException`, `RpcException(Unavailable|DeadlineExceeded)`) as retryable vs fail-fast. Today only a `false` from `TrySaveStateAsync` consumes the retry budget; transient transport blips bypass it and surface immediately. Aligned with the spec ("Retry only confirmed optimistic-concurrency conflicts from guarded-save results; ordinary Dapr/state-store exceptions should fail through the existing projection failure path"), so flagged for design awareness rather than as a defect.
