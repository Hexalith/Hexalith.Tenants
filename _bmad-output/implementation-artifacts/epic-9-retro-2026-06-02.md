## What Went Well

- The planning-only boundary held across all stories. No UI components, pages, backend endpoints, commands, package references, generated files, CSS/theme/token files, resource files, or submodule pointer changes were accepted as Epic 9 deliverables.
- The team reused existing source-of-truth artifacts instead of multiplying them. The dependency map and Phase 2 backlog remained the copy-forward source for dependency IDs, `blockedBy` arrays, owners, fallback decisions, and row readiness.
- Adversarial review found real defects in documentation work. The team fixed the wrong command-route normalization in 9.1, truth-state vocabulary drift in 9.2/9.3, leaked tool-call markup in 9.5, and a planning-boundary violation in 9.7.
- Backend truths were preserved in UI planning: last-owner removal is allowed by design and surfaced as a warning, `RemoveUserFromTenant` is distinct from `RemoveGlobalAdministrator`, recovery is a forward compensating command, and audit evidence composes from the existing audit read model.
- The UI implementation gate is now concrete. ## Challenges

Charlie (Senior Dev): "The biggest friction was keeping plausible UX wording from turning into false backend contracts."

- The route model was easy to normalize incorrectly. Story 9.1 initially rewrote command rows to `POST /api/commands`, but actual EventStore and FrontComposer evidence uses `POST /api/v1/commands`; the unversioned route is only an alias to confirm.
- The vocabulary was dense enough that small wording drift mattered. Accepted, projected, confirmed, audit pending, and audit available cannot collapse into one success state.
- Documentation artifacts were susceptible to authoring artifacts and scope creep. Story 9.5 shipped stray tool-call markup before review fixed it. Story 9.7 initially created an executable test artifact despite being planning-only.
- The Phase 2 backlog uses historical backend evidence keys from a different `9-x`/`10-x`/`11-x`/`12-x` namespace. Story files had to repeatedly warn implementers not to confuse those with sprint-status Epic 9 story IDs.

## Key Lessons

1. Planning-only epics still need adversarial review. Documentation can introduce false routes, false backend invariants, false component availability, and false evidence claims.
2. UI planning must distinguish source-of-truth projection data from local command hints. `accepted`, `projection_pending`, `confirmed`, and `audit_available` are separate user states.
3. A missing UI dependency should block or defer a Phase 2 UI row, not mutate Phase 1 backend scope.
4. Command-capable UI stories need backend-truth checks before UX copy hardens. Last-owner removal, global administrator authority, and compensating recovery each have non-obvious domain rules.
5. Accessibility and localization evidence are readiness gates, not polish. Keyboard/focus, live regions, forced colors, reduced motion, exact timestamps, localizable whole messages, and non-hover disabled explanations must be planned before implementation.
