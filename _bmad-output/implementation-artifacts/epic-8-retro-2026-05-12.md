## Challenges

Charlie (Senior Dev): "Epic 8 exposed a classic documentation trap: planning artifacts were directionally right, but several operational details had drifted from the real system."

- Several acceptance criteria needed interpretation because Aspire now owns setup details that earlier specs described as manual DAPR/EventStore checks.
- The original Keycloak-based JWT mental model did not match the Tenants local dev topology. The docs had to pivot to dev signing key scripts.
- Command payload casing and enum representation were easy to get subtly wrong. The stories resolved this by inspecting the EventStore deserialization path.
- The demo story narrowed "multiple subscribing services" to the existing Sample service. The doc explains the multi-service production model, but the artifact proves the pattern through one concrete subscriber.
- CHANGELOG intentionally keeps the initial release date as `YYYY-MM-DD`, which is appropriate before tagging, but should be filled during the actual release flow.
- The story evidence is strong for source/document consistency, but there is no artifact here confirming that a completely fresh evaluator ran the quickstart and demo from scratch.

Winston (Architect): "The good news is that the architecture held. The caution is that adoption docs become part of the product surface, so they need runtime validation with the same seriousness as code."

## Key Lessons

1. Documentation work needs source verification gates, not just prose review.
2. Adoption docs are product behavior. Incorrect payload casing, auth claims, or endpoint paths are user-facing bugs.
3. The README, quickstart, contract reference, and demo should tell one consistent story from first command to integration confidence.
4. A reproducible script is stronger than a narrative demo, but a script still needs fresh-environment validation before release claims.
5. Stale planning assumptions should be documented as superseded rather than silently erased, so future agents understand why the implementation differs.
6. The next adoption leap is not another document. It is proving the existing docs on a clean machine and recording the gaps.

## Significant Discoveries

- Tenants local development uses a dev signing key JWT path rather than the Keycloak path assumed by earlier quickstart patterns.
- Aspire owns local DAPR state store, pub/sub, and sidecar setup, so manual DAPR component setup is not part of the core quickstart.
- Command payloads use PascalCase inner payload fields and integer enum values because EventStore command deserialization uses default `System.Text.Json` behavior.
- The event contract reference correctly separates command payload formats from event payload/envelope documentation.
- The demo proves the reactive revocation pattern through the existing Sample service; multiple-service fan-out remains an architectural claim supported by the DAPR pub/sub model and should be exercised when more sample consumers exist.
