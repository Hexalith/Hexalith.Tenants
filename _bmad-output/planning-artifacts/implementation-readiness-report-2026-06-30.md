## Step 2: PRD Analysis

### Functional Requirements

FR1: Browse and triage the tenant list. A platform operator can scan, search, filter, sort, and page through tenants. List pagination uses cursor semantics, never offset/limit. Each row shows tenant identity, status, member count, owner count, pending state, and a Truth State Badge with freshness. The list has distinct loading, empty, filtered-empty, error, stale, and degraded states. Sorting or paging must never hide pending or stale markers. Search matches Name or TenantId across the full tenant set through Hexalith.Memories syntactic/BM25 search, requires a server round-trip for non-empty terms, hydrates matched rows through authoritative Tenants ETag/freshness reads, applies exact status filtering, tolerates eventual index consistency, and falls back to cursor view with support-safe notice if Memories is unavailable.

FR2: Open a tenant and return with context preserved. A user can open tenant detail and return to the list with prior selection, filters, sort, and context intact. Deep links to tenant detail are supported.

FR3: Self-audit "My Tenants". A signed-in user can view only the tenants they are authorized to see, including their role and each tenant status.

FR4: Look up a user's memberships. An operator can search for a user, view that user's authorization-scoped tenant memberships, and reach a user from a member row. No visible memberships must render as an explicit empty state, not an error.

FR5: View tenant overview. A user can view one tenant's status, metadata, member summary, and configuration summary. Lifecycle status uses no-color-only encoding and freshness indicators; member and owner counts are shown.

FR6: View tenant configuration read-only. A user can view authorized tenant configuration key/values, grouped by namespace and filtered to namespaces they own or are authorized for. Values outside the caller's prefix are not shown. Sensitive-value display is out of read-MVP scope.

FR7: Copy support-safe identifiers. A user can copy a full identifier or support-safe reference even when visually truncated. Copied content is the full caller-supplied id, not assumed to be a ULID, and must not expose payloads, tokens, correlation ids, or PII.

FR8: Review the member table. A user can review tenant members with role, owner count, status, freshness, and orphan context, read-only. The table must not imply membership mutation or applied role/removal changes, must expose accessible table semantics, and must flag orphan or disabled context.

FR9: See action availability and reasons. A user can see which member actions would be available and, when unavailable, a plain-language Unavailable Action Reason. The MVP reflects availability without enabling mutation. Reasons use the six canonical categories and are inline-visible; tooltips may supplement but are never the only explanation.

FR10: Add a user to a tenant. An authorized user can add a user to a tenant with an explicit role by caller-supplied user id. The add is direct, with no invitation or pending-member step. Adding an already-member user is rejected as `UserAlreadyInTenant` and shown as safe localized text; it is not a NoOp. A corrective add states the intended role. FR10 and FR11 share the historical `ui-09` availability gate.

FR11: Change a member's role. An authorized user can change a member role. Changing to the current role is a NoOp shown as `already applied`; role escalation and `Unknown` targets are rejected with safe localized text. Success is shown only after projection confirmation.

FR12: Remove a user from a tenant. An authorized user can remove tenant access with Consequence Preview, fail-closed gating, elevated friction, and audit proof. Target, tenant, current role, freshness, and authorization are validated before preview. Incomplete preview inputs block submission. The preview states owner-count impact, access revoked, recovery path, audit expectation, and known unknowns. Reducing owner count to zero is elevated friction but not blocked. A target who also holds global-administrator authority raises platform-level friction without conflating command scopes. The remove control is not primary/casual. Already-applied removals read as `already applied`; duplicate submits are deduplicated. The lifecycle tracks `submitted -> accepted -> projection_pending -> confirmed -> audit_pending -> audit_available`; unconfirmable outcomes show `unable to verify`, never success. Every failure mode has a recovery.

FR13: Create a tenant. An authorized operator can create a tenant. Creating an existing tenant id is rejected as `TenantAlreadyExists` with safe text. Success is shown only after projection confirmation.

FR14: Edit tenant metadata. An authorized tenant contributor or global administrator can edit tenant metadata. Every successful edit emits `TenantUpdated`; there is no same-state suppression. Validation errors surface as safe localized field messages.

FR15: Disable or enable a tenant. A global administrator can disable or enable a tenant as a high-impact platform-wide reversible lifecycle control with Consequence Preview. Reissuing the current state is rejected as `TenantLifecycleStateAlreadySet`. Disabled status is an eventually consistent availability signal, and commands targeting a disabled tenant are rejected as `TenantDisabled`. Success is shown only after projection confirmation. Hard destructive tenant deletion is out of scope.

FR16: Set a configuration value. An authorized user can set a namespaced configuration key/value with Consequence Preview required for every eligible configuration mutation in v1. Identical key+value is a NoOp shown as `already applied`. Values over domain limits are rejected as `ConfigurationLimitExceeded`. There is no low-risk-key bypass in v1; future narrowing requires Product/UX/Architecture decision, reason copy, tests, and phasing impact.

FR17: Remove a configuration key. An authorized user can remove a configuration key with Consequence Preview required for every eligible removal in v1. Missing keys surface `ConfigurationKeyNotFound`. Success is shown only after projection confirmation. There is no low-risk-key bypass in v1.

FR18: Review global administrators. An authorized operator can review global-administrator access separately from tenant membership. Tenant owners never see this surface. Data comes from the single fixed-identity `global-administrators` aggregate, not tenant-routed data. Rows show identity and freshness badge.

FR19: Grant or remove a global administrator. An authorized operator can grant a global administrator or remove one except the last. Removing the last global administrator is rejected by the domain as `LastGlobalAdministrator` and reflected as unavailable with safe reason, not friction. Operations use the `global-administrators` scope and are never conflated with tenant membership.

FR20: Browse a tenant audit trail. A user can browse tenant audit entries as a flat, stably ordered list with date and `AuditEventCategory` (`Access`/`Administrative`) filters. The list paginates via cursor, targets approximately 500 events without unacceptable degradation, and renders loading, empty, filtered-empty, and error states distinctly and accessibly. The approved Epic 5 flat DataGrid fallback is the delivered Tenants slice; reusable FrontComposer timeline remains deferred.

FR21: Reach audit from context. A user can reach audit evidence from navigation, tenant row, tenant detail, user lookup, and command result. Each entry lands scoped to the relevant tenant, user, or command.

FR22: View an Audit Evidence Receipt. A user can view a support-safe receipt for a recorded action with actor, target, tenant scope, outcome, timestamp, projection marker, and audit/command reference. The receipt is assembled client-side from structured narrative data, not a new backend receipt endpoint, and never exposes raw payloads, tokens, correlation ids, raw event metadata, or PII. Partial completion shows actual lifecycle state such as `audit pending`, never pre-rendered proof.

FR23: Distinguish audit availability states. A user can distinguish `audit pending`, `audit delayed`, `audit unavailable`, and `missing implementation support`, each with a recovery. None is shown as success. Recoveries include retry, wait, and escalate; missing implementation support reflects `FC-AUD`, not a data error.

FR24: Start a compensating command. From audit evidence, an authorized user can start a forward correction such as "restore intended access" or "start correction". The correction is a new command with its own Consequence Preview and proof. The UI never calls it undo. The original event is untouched. Re-adding an existing member is rejected, so correction previews against current state. Restoring access to a tenant with no remaining membership history relies on empty-tenant bootstrap.

FR25: Preview and link the correction. A user can preview a correction against current state and have original and corrective records linked. The preview reflects current state, both audit records reference each other, and success is shown only after projection confirmation.

Total FRs: 25.

### Non-Functional Requirements

NFR1: Performance and freshness. Reads use cursor pagination and conditional requests so unchanged data is cheap; freshness is surfaced, not hidden. Tenant list/detail/member surfaces target interactive rendering in about 1 second on a warm projection for a typical tenant. Audit targets about 500 events without unacceptable latency; exact budgets are confirmed at implementation.

NFR2: Security and authorization. Authorization is server-enforced at API and domain layers; the UI reflects authorization and never enforces it. The UI must stay safe if it misjudges authorization because the server remains the gate. Role scoping is enforced in projection/query layer.

NFR3: Reliability and consistency. The system is eventually consistent. The UI treats projection as source of truth, re-queries to confirm, and remains correct under at-least-once delivery and projection lag.

NFR4: Observability and testability. Every interactive element and status carries a stable automation selector/component contract that is never keyed on row text or color, enabling robust acceptance and E2E tests.

NFR5: No data-store edits. The UI never edits, deletes, or rewrites events, projections, or state to fix data. Corrections are compensating commands only.

Additional non-functional constraints: UI accessibility baseline is WCAG 2.1 AA with conditional WCAG 2.2 AA target where the pinned Fluent/FrontComposer stack supports it. Keyboard users must complete or exit every modal, preview, table, and command workflow. Screen-reader status must use accessible names, absolute timestamps, table semantics, and live-region politeness that never announces unconfirmed success. Color cannot be the only signal, reduced-motion users cannot depend on animation, all state/copy must be localizable using whole resource strings with named placeholders, and every UI story needs accessibility/localization/responsive/documentation evidence or approved fallback evidence. Support-safety forbids bearer tokens, decoded JWT contents, command payloads, serialized event bodies, raw EventStore metadata, internal correlation ids, stack traces, and real PII from UI, logs, toasts, labels, receipts, and copied values. Responsive behavior is desktop-first, preserves safety-critical columns, and fails closed for high-impact actions when width cannot preserve full safety context.

Total numbered NFRs: 5. Additional non-functional constraints extracted: accessibility, localization, responsive behavior, visual language, privacy, support-safety, FrontComposer dependency readiness, and evidence gates.

### Additional Requirements

- Cross-cutting CP1-CP10 are binding on every command flow: five truth dimensions, fail-closed gating, non-collapse of accepted/confirmed/audit proof, live signals as nudges only, Consequence Preview before destructive action, last-owner friction versus last-global-administrator hard stop, correct-forward recovery, distinct recovery for each failure mode, UI-reflected authorization, and verbatim canonical state sets.
- Canonical Truth State Badge states: `current`, `refreshing`, `aging`, `stale`, `unknown`, `eligible`, `blocked`, `pending`, `accepted`, `confirmed`, `failed`, `audit pending`, `audit available`.
- Canonical freshness states: `current`, `refreshing`, `aging`, `stale`, `unknown`; `aging` is usable with friction, while `stale` and `unknown` block.
- Canonical command lifecycle vocabulary: `eligible`, `previewed`, `submitted`, `accepted`, `rejected`, `already applied`, `failed`, `duplicate`, `timeout`, `unknown`, plus RemoveUserFromTenant `projection_pending`, `confirmed`, `audit_pending`, and `audit_available`.
- Canonical layered feedback states: `request sent (submitted)`, `accepted`, `projection pending`, `confirmed`, `rejected`, `already applied`, `degraded`, `audit pending`, `audit available`, `unable to verify`; `degraded` and `unable to verify` are success-prohibited.
- Unavailable Action Reason categories: `missing permission`, `stale data`, `missing lifecycle support`, `missing consequence preview`, `missing audit proof`, and `high-impact flow not ready`.
- Audit availability states: `audit pending`, `audit delayed`, `audit unavailable`, and `missing implementation support`.
