# Domain fidelity review of the Tenants Management UI PRD

## Overall verdict

FR-24 gives the wrong authority for restoring the last tenant owner. FR-25 also promises a paired audit receipt where the tenant correction workflow explicitly reports missing support. Resolve both before using these requirements as acceptance criteria. The current domain supports deliberate removal of the last tenant owner and protects the last global administrator. FR-12’s “already applied” outcome is supported when a fresh projection proves the target is absent after a membership rejection. [Last-owner regression](../../../../tests/Hexalith.Tenants.Server.Tests/Aggregates/TenantAggregateTests.cs#L1333) · [Last-administrator invariant](../../../../src/Hexalith.Tenants.Server/Aggregates/GlobalAdministratorsAggregate.cs#L50) · [Removal confirmation](../../../../src/Hexalith.Tenants.UI/State/TenantCommands/TenantRemoveMemberCommandSnapshot.cs#L344)

## Findings

- **[high]** Restoring the last owner (FR-24, addendum §D) — The first membership sets a permanent history flag. When the last owner leaves, the aggregate still requires an owner or a global administrator to add a member. With zero owners, a global administrator must perform the authorized restoration. The regression exercises this exact sequence and rejects the outside caller. *Fix:* Describe first-member bootstrap and restoration of a previously populated tenant as separate cases. [Membership history](../../../../src/Hexalith.Tenants.Server/Aggregates/TenantState.cs#L42) · [Add authorization](../../../../src/Hexalith.Tenants.Server/Aggregates/TenantAggregate.cs#L96) · [Regression](../../../../tests/Hexalith.Tenants.Server.Tests/Aggregates/TenantAggregateTests.cs#L1626)
- **[high]** Paired audit proof (FR-25, §7.9) — After projection confirmation, the tenant correction flow preserves the original evidence, clears the proof link and reports `MissingSupport`. The global-administrator flow can expose a pair when it independently verifies the attempt and system audit evidence in the same circuit. *Fix:* Specify the observable outcome for each flow. Record deterministic tenant proof pairing as outstanding if it remains a product requirement. [Superseded Story 5.6 disposition](../../../implementation-artifacts/5-6-preview-and-confirm-correction-with-linked-proof.md#L11) · [Tenant proof handling](../../../../src/Hexalith.Tenants.UI/State/TenantAudit/TenantCorrectionPreviewSnapshot.cs#L410) · [Administrator receipt requirements](../../../implementation-artifacts/spec-5-7-correct-global-administrator-authority-from-audit-evidence.md#L81)
- **[medium]** Global-administrator correction availability (§7.9) — The PRD still describes Story 5.7 verification and its pagination follow-up as pending. The tracker records completion, the audit page mounts the correction panel, and tests exercise recovery after a target changes or the panel remounts. *Fix:* Update the delivery status and specify the remaining per-attempt gates for authority, complete evidence, and last-administrator protection. [Story status](../../../implementation-artifacts/sprint-status.yaml#L82) · [Pagination resolution](../../../implementation-artifacts/sprint-status.yaml#L329) · [Audit page](../../../../src/Hexalith.Tenants.UI/Components/Pages/TenantAuditPage.razor#L266) · [Recovery tests](../../../../tests/Hexalith.Tenants.UI.Tests/Components/GlobalAdministratorCorrectionPanelRecoveryTests.cs#L39)
- **[medium]** Disabled tenants (FR-15, addendum §D) — The blanket rejection rule contradicts the lifecycle. A global administrator can enable a disabled tenant. A second disable returns the already-set rejection, and an authorized access refresh can emit a snapshot carrying disabled status. *Fix:* Limit the disabled-tenant rejection to the affected mutations and name the lifecycle and snapshot outcomes. [Lifecycle handlers](../../../../src/Hexalith.Tenants.Server/Aggregates/TenantAggregate.cs#L58) · [Snapshot rule](../../../../src/Hexalith.Tenants.Server/Aggregates/TenantAggregate.cs#L245)
- **[medium]** Role promotion (FR-11, addendum §D) — “Role escalation” could be read as prohibiting promotion between valid tenant roles. An authorized owner can promote a reader to contributor. The rejection named `RoleEscalation` applies to the unassignable `Unknown` sentinel or an out-of-range target role. *Fix:* Specify actor authorization and allowed target roles separately, with a valid promotion example. [Role handler](../../../../src/Hexalith.Tenants.Server/Aggregates/TenantAggregate.cs#L198) · [Owner promotion regression](../../../../tests/Hexalith.Tenants.Server.Tests/Aggregates/TenantAggregateTests.cs#L1455)
- **[low]** Metadata editing (FR-14, addendum §D) — “Contributor or global administrator” omits tenant owners when read as a list of eligible roles. The handler treats contributor as a minimum and the owner test succeeds. *Fix:* Include contributors, owners and global administrators explicitly.
