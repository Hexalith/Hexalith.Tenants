# Tenants UI Phase 2 Story Backlog

Owner: Hexalith.Tenants product and UX planning
Status: Phase 2 planning/readiness artifact
Last reviewed: 2026-05-20

This backlog turns the Epic 12 dependency map into copy-forward candidate Tenants Admin UI stories. It is planning output only: it does not create sprint-status entries, implementation story files, UI screens, `Hexalith.FrontComposer` components, backend endpoints, command/query contracts, package changes, submodule pointer changes, or Phase 1 release gates.

Rows use current repository terminology. `Hexalith.FrontComposer` is the checked-out UI dependency. `FrontShell`, `@hexalith/ui`, `useCommand`, `<AuditTimeline>`, and `<ConsequencePreview>` are legacy or UX aliases until current `Hexalith.FrontComposer` evidence proves a concrete contract.

## Scope Boundary

- Candidate rows consume completed backend evidence from Epics 9 through 11 and earlier backend stories. They must not duplicate backend requirements unless a product or architecture change explicitly reopens scope.
- Candidate rows with unresolved `blockedBy` entries remain `planning-only` or `blocked`; none of those rows are implementation-ready.
- `blockedBy` is always a literal array. Use `blockedBy: []` only when backend evidence is complete, FrontComposer dependencies are `available` or `approved-fallback`, and no unresolved UX, auth, navigation, accessibility, localization, documentation, or contract dependency remains.
- `ready-with-approved-fallback` requires a named approved fallback, a decision owner, and evidence. Proposed or deferred fallback decisions keep the row `planning-only` or `blocked`.
- Grouped audit mode, server-side anomaly scoring, bulk provisioning, and advanced analytics stay out of this first-slice backlog until product explicitly promotes them.

## Field Encoding Conventions

All array-valued cells use literal `[item1, item2, ...]` form. Cells do not repeat the column name as a prefix — the column header is the field identity.

| Field | Cell form | Grammar |
| --- | --- | --- |
| `backendEvidence` | `[token, token, ...]` | Each token is one of: bare story key (e.g., `5-3-query-endpoints-and-authorization`), `endpoint:<METHOD> <path>` (e.g., `endpoint:GET /api/tenants`), `command:<CommandName>` for single commands, `commands:<Name1>\|<Name2>` for sibling commands sharing a story, or `docs:<repo-relative-path>` for documentation evidence. Bare story keys must match files under `_bmad-output/implementation-artifacts/`. |
| `frontComposerDependencies` | `[<FC-ID>: <readiness>, ...]` | Each entry pairs a stable FC-ID with one of the Story 12.1 readiness values: `available`, `needs-confirmation`, `missing`, `planned`, or `approved-fallback`. Order is not significant. |
| `blockedBy` | `[<FC-ID>, ...]` or `[]` | Each entry is a stable FC-ID or backend story key. `[]` is only valid when no unresolved dependency remains; see Scope Boundary. |
| `readiness` | enum | One of: `ready`, `ready-with-approved-fallback`, `planning-only`, `blocked`. |
| `fallbackDecision` | enum | One of: `approved`, `proposed`, `deferred`. The prose description belongs in `fallbackNotes`, not concatenated to the enum value. |
| `fallbackNotes` | free text | One-line kebab-style or prose summary of the proposed or deferred fallback. May be `none` when no fallback is recorded. |
| `evidenceSource` | `[<repo-relative-path>, ...]` | Each entry is a repo-relative path. No local absolute paths, no secrets, no bearer tokens, no raw tenant/user production data, no generated build artifacts. |

## Readiness Order

### Ready

No rows currently qualify. A future row may move here only when `blockedBy: []` is justified by completed backend evidence, current FrontComposer evidence, story-specific accessibility/localization/documentation evidence, and no unresolved contract decisions.

### Ready With Approved Fallback

No rows currently qualify. Product/UX and `Hexalith.FrontComposer` have not approved a row-specific fallback for layout, command feedback, audit timeline, consequence preview, tokens, accessibility, localization, or documentation evidence.

### Planning Only

Current order: `ui-01`, `ui-02`, `ui-03`, `ui-04`, `ui-05`, `ui-06`, `ui-07`, `ui-08`, `ui-09`.

These rows have completed backend evidence or available table evidence, but they still carry unresolved FrontComposer, accessibility, localization, documentation, command, or token dependencies. None of them carries a deferred fallback or `FC-AUD`/`FC-CNS: missing`, so they remain `planning-only` rather than `blocked`. They may be refined into implementation stories only after the row's `blockedBy` array shrinks to `[]` or a named approved fallback moves the row to `ready-with-approved-fallback`.

### Blocked

Current order: `ui-10`, `ui-11`, `ui-12`, `ui-13`, `ui-14`, `ui-15`.

A row is `blocked` (not just `planning-only`) when at least one of the following holds: (a) `blockedBy` includes `FC-AUD` or `FC-CNS` with the dependency's readiness recorded as `missing`; or (b) the row carries a `deferred` `fallbackDecision` for a high-impact or destructive workflow with no approved alternative. `ui-10` qualifies on both branches (`FC-CNS: missing` plus deferred high-impact-classification fallback); `ui-11`/`ui-12` qualify on (a); `ui-13`/`ui-14`/`ui-15` qualify on (a) and (b). Do not assign blocked rows as implementation-ready until the missing deliverables or approved fallbacks are recorded with owners and evidence.

## Future Story Checklist

Every future Phase 2 Tenants UI story must populate the same 12 mandatory candidate-row fields as a `ready` or `ready-with-approved-fallback` candidate. The checklist below maps each requirement to its row field.

- `blockedBy`: exact dependency IDs or backend story keys in literal array form (see Field Encoding Conventions). Never use prose-only blockers.
- `backendEvidence`: literal array of completed story keys, `endpoint:`, `command:`, `commands:`, or `docs:` tokens per the documented grammar. Do not duplicate backend requirements unless product/architecture explicitly reopens scope.
- `frontComposerDependencies`: `[<FC-ID>: <readiness>, ...]` using stable IDs from this backlog and Stories 12.1-12.3 plus Story 12.1 readiness vocabulary (`available`, `needs-confirmation`, `missing`, `planned`, `approved-fallback`). Each row's `frontComposerDependencies` MUST include `FC-A11Y`, `FC-L10N`, and `FC-DOC` or carry a row-level explanation of why one is omitted, with approved evidence (this enforces Story 12.4 AC9).
- `fallbackDecision`: enum value `approved`, `proposed`, or `deferred`. `proposed` and `deferred` prevent the row from being `ready` or `ready-with-approved-fallback`.
- `fallbackNotes`: short description of the proposed/deferred/approved fallback. Use `none` when no fallback is recorded.
- `decisionOwner`: accountable role or group for every unresolved dependency in this row. When multiple owners apply (e.g., layout vs. command), prefer naming the dominant owner here and disambiguating per-dependency in the Deferred Decisions table.
- `evidenceSource`: literal array of repo-relative paths. No local absolute paths, secrets, bearer tokens, raw production tenant/user data, generated build artifacts, or transient logs.
- `readiness`: enum value, never set to `ready` or `ready-with-approved-fallback` while any of: `blockedBy` is non-empty, `fallbackDecision` is `proposed` or `deferred`, `decisionOwner` is missing, or `evidenceSource` is empty.
- `workflow`: must preserve role-aware UX, tenant/user context, source-of-truth projection re-query behavior, no-color-only status behavior where applicable, deployment-auth assumptions from Epic 11, and bounded copy. Stories must not expose command payloads, bearer tokens, serialized command bodies, stack traces, raw EventStore metadata, internal correlation IDs, or PII.
- `sequencingPriority`: stable `P##` identifier for backlog ordering; rebuild the sort after any row is promoted or downgraded so dependency-ready rows precede blocked rows unless product accepts the sequencing risk explicitly.

When recording a future story row, do not invent new column names. The 12 fields above are the complete row schema; story-level cross-cutting concerns (accessibility, localization, documentation, Phase 1 release safety, tenant/user boundary) are tracked through the existing fields rather than parallel columns.
