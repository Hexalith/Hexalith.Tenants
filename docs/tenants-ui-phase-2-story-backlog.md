# Tenants UI Phase 2 Story Backlog

Owner: Hexalith.Tenants product and UX planning
Status: Phase 2 planning/readiness artifact
Last reviewed: 2026-05-20

This backlog turns the Epic 12 dependency map into copy-forward candidate Tenants Admin UI stories. It is planning output only: it does not create sprint-status entries, implementation story files, UI screens, `Hexalith.FrontComposer` components, backend endpoints, command/query contracts, package changes, submodule pointer changes, or Phase 1 release gates.

Rows use current repository terminology. `Hexalith.FrontComposer` is the checked-out UI dependency. `FrontShell`, `@hexalith/ui`, `useCommand`, `<AuditTimeline>`, and `<ConsequencePreview>` are legacy or UX aliases until current `Hexalith.FrontComposer` evidence proves a concrete contract.

## Scope Boundary

- Candidate rows consume completed backend evidence from Epics 9 through 11 and earlier backend stories. They must not duplicate backend requirements unless a product or architecture change explicitly reopens scope.
- Candidate rows with unresolved `blockedBy` entries remain `planning-only` or `blocked`; none of those rows are implementation-ready.
- `blockedBy` is always a literal array. Use `blockedBy: []` only when backend evidence is complete, FrontComposer dependencies are `available` or `approved-fallback`, and no unresolved UX, auth, navigation, accessibility, localization, documentation, or contract dependency remains.
- `ready-with-approved-fallback` requires a named approved fallback, a decision owner, and evidence. Proposed or deferred fallback decisions keep the row `planning-only` or `blocked`.
- Grouped audit mode, server-side anomaly scoring, bulk provisioning, and advanced analytics stay out of this first-slice backlog until product explicitly promotes them.

## Readiness Order

### Ready

No rows currently qualify. A future row may move here only when `blockedBy: []` is justified by completed backend evidence, current FrontComposer evidence, story-specific accessibility/localization/documentation evidence, and no unresolved contract decisions.

### Ready With Approved Fallback

No rows currently qualify. Product/UX and `Hexalith.FrontComposer` have not approved a row-specific fallback for layout, command feedback, audit timeline, consequence preview, tokens, accessibility, localization, or documentation evidence.

### Planning Only

Current order: `ui-01`, `ui-02`, `ui-03`, `ui-04`, `ui-05`, `ui-06`, `ui-07`, `ui-08`, `ui-09`, `ui-10`.

These rows have completed backend evidence or available table evidence, but they still carry unresolved FrontComposer, accessibility, localization, documentation, command, token, or classification dependencies. They may be refined into implementation stories only after the row's `blockedBy` array shrinks to `[]` or a named approved fallback moves the row to `ready-with-approved-fallback`.

### Blocked

Current order: `ui-11`, `ui-12`, `ui-13`, `ui-14`, `ui-15`.

These rows depend on `FC-AUD` or `FC-CNS` missing evidence, or on high-impact command behavior that has no approved fallback. Do not assign them as implementation-ready until the missing deliverables or approved fallbacks are recorded with owners and evidence.

## Future Story Checklist

Every future Phase 2 Tenants UI story must include these fields before it can be considered for development:

- `blockedBy`: exact dependency IDs or backend story keys in array form, never prose-only blockers.
- `backendEvidence`: completed story keys, endpoints, commands, queries, or documentation evidence. Do not duplicate backend requirements unless product/architecture explicitly reopens scope.
- `frontComposerDependencies`: stable IDs from this backlog and Story 12.1 through 12.3, with readiness values such as `available`, `needs-confirmation`, `missing`, `planned`, or `approved-fallback`.
- `fallbackDecision`: `approved`, `proposed`, or `deferred`, with owner and evidence. `proposed` and `deferred` prevent `ready` and `ready-with-approved-fallback`.
- `decisionOwner`: accountable role or group for every unresolved dependency.
- `a11yL10nDocCoverage`: explicit `FC-A11Y`, `FC-L10N`, and `FC-DOC` coverage, or a row-specific explanation with approved evidence.
- `phase1BlockerStatus`: confirmation that UI-only dependencies do not block Phase 1 backend/package/release work.
- `tenantUserBoundary`: role-aware UX, tenant/user context, source-of-truth projection re-query behavior, and no-color-only status behavior where applicable.

Future stories must preserve tenant/user isolation, role-aware controls, projection/query source-of-truth behavior, deployment-auth assumptions from Epic 11, and safe bounded copy. They must not expose command payloads, bearer tokens, serialized command bodies, stack traces, raw EventStore metadata, internal correlation IDs, local absolute paths, raw production tenant/user data, generated artifacts, or transient logs.
